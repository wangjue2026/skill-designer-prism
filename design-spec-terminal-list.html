2. 主场景清单与现状痛点

场景（编号. 名称）主要角色用户 Job现状卡点
S1. 资产盘点与对账 安全管理员
审计人员		 维护一份清晰可用、能对外交账的资产台账（入库、分类、打标由客户端注册与其他模块承担，本页负责呈现与对账）
  • 状态串味：在线/离线是连接态，启用/禁用是管理态，升级成功/失败是版本态，三者挤在一列就分不清"这台是掉线了还是被我禁了"
  • 信息要跨处拼：版本、最后活跃、首次接入分散在不同列与不同页面，核对一次要来回切
  • 导出口径说不清：导出的是勾选的、筛选的还是全部；字段还与列表不一致，交出去要再解释
S2. 批量运维 客户端运维管理员 把一批终端推到目标状态——选批、预检、下发、逐台结果确认、失败重试，没成的有结论
  • 不知道能不能升：点下去才发现离线、不兼容或有冲突任务，只能一个个试
  • 误操作代价高：禁用/卸载影响终端侧识别与控制能力，缺少影响面预告
  • 只有任务级结果：看到"部分成功"却不知道是哪几台、失败在哪一步
  • 重试粒度粗：整批重跑会把已成功的终端再跑一遍
S3. 资产异常处置 安全管理员
客户端运维管理员		 把问题终端处理干净——定位到具体终端、判明性质、就地处置、留下回执
  • 筛不动：只有单一关键词框，无法按操作系统 + 状态 + 是否待升级组合收窄
  • 筛完就丢：刷新后条件被清空，重复筛选消耗耐心
  • 处置与回执脱节：行内与批量两处入口，结果还要去任务台账里翻

3. 资产盘点 / 批量运维 / 异常处置：体验目标

  • 台账自己保持准确：终端版本、启停状态与在线情况随实际情况收敛到台账上，管理员不再需要定期逐台核对；异常的终端自己浮出来并带上原因，人只在需要拍板时才被叫来——验收方式：连续一个月不做主动核对，仍能随时交出一份与当前状态一致的清单，且每一台异常都有归属。
  • 一批终端从下达到到位，不需要人盯：能升的自己升，升不了的自己给出原因与下一次动作，失败的只把没成的那几台交回给人处理；原来"发出去 → 回列表 → 开任务页 → 找失败 → 整批重试"整段盯人流程消失——验收方式：一次下发 50 台，人只需要处理不超过 3 台例外，其余无需回看。
  • 危险的改动有人替你把关：禁用、卸载、升级这类会削弱终端能力的动作，动手之前就能看到会影响哪些终端、哪几台做不了、为什么；执行后只承诺"已下发"，结果以台账为准——验收方式：给 3 台不可升级终端，用户不点确认就能说出各自为什么升不了。
  • 交账不用再整理一遍：对外那份清单与系统里的台账始终是同一份，范围与口径写在出处上，交出去不需要再解释"这是怎么筛的"——验收方式：任何人拿到导出文件，能自己说出它是按什么范围、哪些字段导出来的。
📌 本版实现水位：界面内闭环（状态可信、例外可见、动作有确认与回执）。工作级目标里的"自动收敛、自动重试、自动派单"依赖引擎能力，本版只做到"人不用找，但还得人点"；差距留到下一版，不在本文假装已经做到。

Part2　需求解决方案全景

6. 设计决策经验匹配与采纳

6.1 需求类型分析

  • 需求类型定性：Type-01 对象与资产管理类。判据：主键是终端实体（terminalId），长期存在并带台账属性（接入 / 启用 / 卸载 / 删除），需按状态批量维护，有明确生命周期。
  • 业务属性与严肃度：终端是安全能力的落点，中高严肃度。禁用与卸载会直接影响终端侧的识别与控制能力，删除会丢失台账记录；但日常查看、筛选、刷新属高频低风险，不能一律上重确认。
  • 色彩基调：超浅底 #F7F9FC 分区、白底承载、1px 细线去框线化；状态一律"浅底 + 深字 + 浅边框"三元组；只有品牌蓝主按钮 #1C6EFF，不使用红色实心按钮。
