# 1.3 体验突破点拆解演练集

> 💡 **用途**：验证 [1.3 体验突破点拆解](../1.3-体验突破点拆解.md) 的方法稳不稳，同时验证 [四类工作类型经验](../方案设计思考经验/) 能否扫出目标之外的机会点。
>
> 📐 **每个案例只跑 1.3**：给场景 + 一句体验目标（+ 现状痛点），出突破点清单与分档点子。不走 1.1 旅程、不走 1.2 目标推演、不碰后续布局与草图。
>
> 🛑 **必标来源**：每个突破点都要标清来自「出入口 1（目标）」还是「出入口 2（工作类型经验）」。扫不出净增量，就说明那类经验在这一类场景上不好用。
>
> 🚧 **状态**：进行中，案例数 3 / 目标 ~10。
>
> 🔧 **模板口径变更（2026-10-20）**：案例 A~C 是用**旧模板**跑的（无来源列、无裁剪规则、无指标回校）。A~C 保持原样不动——它们是缺口的第一手证据。**案例 D 起统一用新模板**，新模板在旧模板基础上加了四样：来源列（经验净增量加粗）、候补 / 裁剪记录行、硬指标翻感受点、指标回校列。
> 这四样的来源就是下面「已发现缺口」表的 1~5 条，现已修进 [1.3](../1.3-体验突破点拆解.md)，见文末「修复登记」。

## 案例 A：SASE 合规检测任务制定

**场景**：终端管理 ➔ 终端管控 ➔ 合规基线检测 ➔ 新建检测任务（抽屉内配规则、选范围、定周期）
**体验目标（拟）**：让 0 基础的安全运维管理员不翻文档、不靠别人，自己配出一条敢下发的检测任务。
**现状痛点**：手填进程名 / 注册表 / 软件 Hash，拼错就漏报；选完范围不知道会打到多少台。
**命中工作类型**：① 配置运维

### 1. 感受点

| 感受点 | 什么意思 |
| :--- | :--- |
| 不查 | 不用翻文档、不用问人就知道这一项在查什么 |
| 不冒进 | 动手前就知道这一下会打到谁 |
| 不发虚 | 发出去之后知道成没成 |

### 2. 突破点

| # | 面对的感受点 | 突破点（体验语言） | 来源 |
| :---: | :--- | :--- | :--- |
| B1 | 不查 | 让人不用懂底层参数，也能把"要查什么"说清楚 | 目标 + ①原则1 看得懂 |
| B2 | 不冒进 | 让人动手前就知道这一下会打到谁、会不会误伤 | 目标（部分）+ ①原则3 配不错 |
| B3 | 不查 / 不重复 | 让人配过一次的规则组，下次直接拿来用 | **①原则2 填得少（目标没提）** |
| B4 | 不发虚 | 让人提交后马上知道谁收到了、谁没收到 | **①原则4 配完敢信（目标没提）** |

### 3. 分档点子

**B1 不用懂参数也能说清楚**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 软件名下拉选，字段旁带解释 | 还得自己判断选哪个 |
| 优化版 | 按"防病毒 / 防泄密 / 防外联"分组预置，勾选即填完 | 不用填 exe 名 |
| 创新版 | 只说"研发机不许装翻墙工具"，系统出规则草案，人确认 | 不用认字段 |
| 变革版 | 基线由系统按等保要求统一发布，租户只选"采纳 / 调整" | 不用配规则 |

**B2 动手前知道打到谁**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 选完范围显示预估台数 | 台数有了，别的不知道 |
| 优化版 | 预估拆成在线 / 离线 / 系统不支持，并提示"父部门以后新增的终端也会被扫到" | 不用自己算 |
| 创新版 | 提交前给影响预览：哪些会被命中、哪些会被自动阻断（零信任联动后果先看到） | 不用凭经验猜 |
| 变革版 | 先在观察模式跑一轮，只统计不阻断，看完真实命中再转正式 | 不用提前赌 |

**B3 配过的直接复用**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 任务可复制 | 每次复制完还要改 |
| 优化版 | 规则组独立成模板，可命名 | 不用重勾 |
| 创新版 | 模板库按部门 / 场景推荐，套完只改差异 | 不用记上次配了啥 |
| 变革版 | 系统按资产画像自动出整套基线（研发 / 财务 / 外包各一套） | 不用挑模板 |

**B4 发出去成没成**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 任务状态显示"已下发" | 只能看个总状态 |
| 优化版 | 三态进度（已检测 / 违规 / 离线跳过）+ 失败终端可查 | 不用猜 |
| 创新版 | 给出"谁没收到、为什么没收到"清单，可就地补发 | 不用去别处对账 |
| 变革版 | 终端上线自动补检，人不用关心发没发到 | 不用管 |

### 4. 观察

| 观察点 | 结果 |
| :--- | :--- |
| 入口 2 净增量 | 有。B3、B4 目标里完全没有；"父部门以后新增终端也会被扫到"也是纯经验补的 |
| 高位档 | 4 条都能到创新版。**变革版全部要改目标**——"人自己配得对"这个量级撑不到"不用人配" |
| 混类边界 | 只命中 ①，无重复命中 |
| 反常 | ①写着"别四条全上"，但任务型配置页四条原则全中。这条经验在"新建任务"页面上不成立 |
| 落表缺口 | 1.3 交付模板缺"来源"列；`别四条全上`的判据缺适用条件 |

## 案例 B：数据安全产品多场景研判

**场景**：API 安全、用数行为、数据风险三条线各自的告警研判页
**体验目标**：多场景研判体验统一，举证清楚，关键信息拿得快，客户运营人员可借助 AI 辅助独立完成研判。
**角色假设**：客户运营人员（安全运营服务商里对接客户的人）。若该角色不对外交付结论，④ 价值感知不扫。
**命中工作类型**：② 运营分析

### 1. 感受点

| 感受点 | 什么意思 |
| :--- | :--- |
| 不用重学 | 换个场景，不用重新找位置、重新记叫法 |
| 看得清依据 | 不用自己拼证据，就能接受这个结论 |
| 拿得快 | 判这一条要用的信息，打开就在 |
| 不求人 | 不用问专家、不用等后台，自己就能定 |

### 2. 突破点

| # | 面对的感受点 | 突破点（体验语言） | 来源 |
| :---: | :--- | :--- | :--- |
| B1 | 不用重学 | 让人换一个场景，研判还是同一套顺序、同一个位置 | 目标（统一） |
| B2 | 看得清依据 | 让人不用自己拼证据，就能看出凭什么这么判 | 目标（举证清晰） |
| B3 | 拿得快 | 让人打开就看到该判的那几条，重复的、低价值的自动收走 | 目标（高效）+ **②原则3 该看的浮上来** |
| B4 | 不求人 | 让人自己就能把结论定下来——AI 把疑点摆出来等人确认，不替人下结论 | 目标（独立 + AI 辅助） |
| 候补 | — | 让人判过一次的同类，下次能调出来直接参照 | **②原则5 判过的能留下（目标没提）** |

> 候补那条超出 1.3 的"2~4 处"上限（**当时口径**；2026-10-22 已放宽为 2~5，本案例 4 处保留 + 1 处候补 = 5 处，按新口径刚好压线，待重跑确认是否纳入）。目标一句话塞了四个诉求，扫出来必然超。

### 3. 分档点子

**B1 换场景不重学**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 三条线各自有结论区，位置和叫法不统一 | 每个场景重新找 |
| 优化版 | 统一顶部结论条：结论、置信度、关键依据、建议动作，位置固定 | 不用找，但要重新理解字段 |
| 创新版 | 统一研判单——不管从哪条线进来，都落到同一张单子，只是字段不同 | 只学一套 |
| 变革版 | 研判单由系统按场景生成，人只填"待确认"那几格 | 不用学 |

**B2 证据不用自己拼**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 证据在详情页，人自己对照结论 | 自己拼 |
| 优化版 | 结论旁边列 3 条关键证据，标出哪条是判定的关键 | 不用翻，但还得自己串 |
| 创新版 | 证据按时间线串成一条链：谁、从哪、动了什么数据、影响到谁，结论挂在链上 | 不用串 |
| 变革版 | 同时给反证提示：这条证据有没有可能是误报、差哪条才能排除 | 不用自己想反例 |

**B3 打开就看该看的**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 列表给全量，能筛能排 | 自己筛 |
| 优化版 | 默认按风险排，同类合并成一条并标"×37" | 不用逐条看重复的 |
| 创新版 | 打开就是"需要我判的"，系统已把能自动判的判完并分级 | 只看该看的 |
| 变革版 | 系统直接给结论和处置建议，人只审抽样和例外 | 不用逐条判 |

**B4 独自定结论**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | AI 给一句摘要 | 还得自己判 |
| 优化版 | AI 给疑点清单：还差哪几条信息、建议去哪看 | 不用自己想缺什么 |
| 创新版 | AI 按场景把要问的问题排好，人顺着答完，结论自动成型 | 不用自己想思路 |
| 变革版 | AI 出初判和置信度，人只处理低置信的 | 不用从零判 |

### 4. 观察

| 观察点 | 结果 |
| :--- | :--- |
| 入口 2 净增量 | 有。B3 的"重复合并成一条""能自动判的判完只留该看的"，目标里只有个"快"字，没有"少看"。B1 创新版（统一研判单）也是 ②原则4 带出来的 |
| 高位档 | 能到创新版，**变革版这次放得出来**——目标里有"AI 辅助"，等于提前授权"AI 初判、人审例外"。与案例 A 相反：A 的目标是"人自己配得对"，变革版全被卡住 |
| 混类边界 | 命中 ② 为主。③ 只在"研判完要流转处置"时成立，本案目标只到"完成研判"，不扫；④ 只在"结论要交付客户"时成立，**待确认** |
| 超出上限 | 扫出 5 处，超了上限，1.3 没有裁剪规则 |
| 落表缺口 | 缺"来源"列；模板是单场景（Sx）写法，"多场景一致"这类目标没地方表达 |

## 案例 C：总部对分支与租户的全局掌握与批量管理动作下发

**场景**：总部安全运营的总览页，以及从总览页往下发管理动作（周期巡检、按风险处置、覆盖全部分支与租户）
**体验目标**：总部一屏掌握全部分支与租户的安全状况；管理动作可按风险高低排序下发；全局巡检耗时从 2 天降到 ≤ 10 分钟；管理动作覆盖率达 100%。
**命中工作类型**：④ 价值感知（主）+ ② 运营分析 + ① 配置运维 + ③ 排障闭环（条件命中，见观察）

### 1. 感受点

| 感受点 | 什么意思 |
| :--- | :--- |
| 一屏 | 不用切租户、不用翻分支、不用守着看进度 |
| 有序 | 不用自己比，就知道先管谁 |
| 不冒进 | 批量动作发出去之前，知道会碰到谁 |
| 不漏底 | 不用点名对账，就知道谁真被管住了 |

> 🛑 **指标不是感受点**：2 天 → 10 分钟、100% 覆盖率是**指标**，翻成感受才是"不用守""不用对账"。

### 2. 突破点

| # | 面对的感受点 | 突破点（体验语言） | 来源 |
| :---: | :--- | :--- | :--- |
| B1 | 一屏 | 让人不用切换、不用守着，也能一屏看清每个分支 / 租户现在怎么样、好坏在哪、巡检跑到哪 | 目标（一屏 + 耗时）+ ④原则1、原则3 好坏要有参照 |
| B2 | 有序 | 让人不用自己比，就知道先管谁、后管谁 | 目标（按风险排序）+ **②原则3 该看的浮上来** |
| B3 | 不冒进 | 让人把动作发出去之前，就知道会碰到谁、会不会断业务 | **①原则3 配不错（目标没提）** |
| B4 | 不漏底 | 让人不用点名对账，就知道谁被管到了、发出去成没成、改没改好 | 目标（100% 覆盖）+ ①原则4 配完敢信 + ③原则4 闭环到哪算完 |

### 3. 分档点子

**B1 一屏看清**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 按租户 / 分支分别进各自的页看 | 自己切、自己记 |
| 优化版 | 总部汇总表：全部分支与租户一行一个，带状态、告警数、合规率，可排序 | 不用切，但要自己找问题 |
| 创新版 | 一屏三层：顶部结论条（现在怎么样、挡住了什么）→ 分支 / 租户排行（带基线对比）→ 待处理动作；巡检进度常驻顶部 | 不用找、不用比、不用守 |
| 变革版 | 系统直接给出"今天该管的三件事"和理由，其余默认收起，人只确认 | 不用看全量 |

**B2 先管谁**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 列表能按风险列排序 | 自己排、自己判断 |
| 优化版 | 默认按风险 × 影响面排，同类重复合并成一条 | 不用排 |
| 创新版 | 给出处置优先级清单，每条带"为什么先做它"（影响多少终端、是否在扩散）+ 建议动作 | 不用判断顺序，只确认 |
| 变革版 | 低风险动作由系统按规则自动下发，人只处理要人工决策的 | 不用逐条下发 |

**B3 发之前知道碰到谁**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 二次确认弹窗写"将对 3,200 台终端下发" | 只有一个数 |
| 优化版 | 下发前给影响面：涉及多少分支 / 租户 / 终端、多少离线、会影响哪些业务 | 不用自己估 |
| 创新版 | 影响预览 + 先小范围试：选一个分支先发，看完结果再全量 | 不用赌 |
| 变革版 | 默认灰度：系统按分支分批推进，异常自动停下等人看 | 不用管分批 |

**B4 谁真被管住了**

| 档位 | 点子 | 用户还出什么力 |
| :---: | :--- | :--- |
| 基线版 | 状态列显示"已下发 / 失败" | 自己数 |
| 优化版 | 覆盖率汇总：应管 / 已管 / 未管，未管的给原因（离线、未装客户端） | 不用对账 |
| 创新版 | 覆盖率按分支 / 租户拆开，未覆盖的就地补发；"发到了"和"改好了"分开看 | 不用去别处查 |
| 变革版 | 新终端上线、新租户接入自动纳入管控，覆盖率常驻 100%，人只看例外 | 不用管 |

### 4. 观察

| 观察点 | 结果 |
| :--- | :--- |
| 入口 2 净增量 | 有，而且最值钱的一条在最前面：**B3 完全来自 ①**。目标只承诺"覆盖率 100%"，没说"别把谁的业务断了"——批量下发动作恰恰是误伤代价最大的地方 |
| 混类边界 | 首次四类混命中：④ 出"好坏参照"，② 出"降噪合并"，① 出"影响面 + 覆盖反馈"，③ 出"发到 ≠ 改好"。四类没有重复表述，分得开 |
| ③ 的条件命中 | 只有当管理动作带**跟踪整改到恢复**时才扫 ③；若动作只到"下发通知"就结束，③ 不扫，否则会把闭环硬塞进来 |
| 高位档 | 4 条都能到创新版，变革版也放得出。因为目标里有"2 天 → 10 分钟""100% 覆盖"这种硬承诺，本身就在要求系统接管执行 |
| 指标的反作用 | 目标带硬指标时，高水位点子必须仍然满足指标。比如"系统自动下发"必须同时说明 10 分钟内完成，否则点子只是好看。1.3 现在没有这一步校验 |
| 落表 | 与案例 B 同一处缺口：单场景写法装不下"跨分支 / 跨租户"；来源列缺失 |

## 已发现的模板与经验缺口

| # | 缺口 | 来自 | 建议 |
| :---: | :--- | :---: | :--- |
| 1 | 1.3 交付模板无"来源"列 | A、B | 模板加一列「来源：目标 / 工作类型 + 原则编号」 |
| 2 | 模板按单场景（Sx）写，跨场景一致性无处表达 | B | 模板加"跨场景共用"的写法，或允许一个突破点挂多个场景 |

| 4 | "别四条全上"缺适用条件 | A | 补充：新建 / 配置类任务页常四项全中，此时按"错了会怎样"排优先级，不当作验收单 |
