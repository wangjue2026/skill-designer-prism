# 1.2 体验目标定义（每主场景一句）

> 💡 **中枢定位**：
> 本文档是【方案系统设计主线】1.1 之后的**体验目标定义环节**：承接 1.1 的场景拆解与痛点，产出**每个主场景一句**的体验目标。
> 产物只服务两个下游——1.3 突破点拆解（原话抠感受点）与《设计说明书》Part1 第 3 节（原话落位）；**不单独定义交付形态，不做方案选型**。

---

## 一、输入：1.1 的产物为主，需求指令定边界

### 1. 输入来源与用途

| 来源 | 取什么 | 用来定什么 |
| :--- | :--- | :--- |
| **1.1 需求理解与场景拆解（主输入）** | 主场景清单（编号. 名称）、各场景的 Job、现状痛点清单（名称 + 严重度 + 现状基线）、主角色 | 目标对着哪个场景、站在哪个 Job 上、痛点与现状 A 从哪来 |
| **需求指令**（需求文档 / PRD / 评审版需求说明） | 立项目标、Non-Goals、已确认的量化规格、字段与口径 | 目标边界（不得越过 Non-Goals）、取已确认数值、照抄业务字面 |

> 🛑 不引外部素材、不预设行业做法。1.1 与需求指令冲突时，以需求指令为准，并回标 1.1 修正。

### 2. 写之前先对齐四件事

| 对齐什么 | 决定目标里的什么 |
| :--- | :--- |
| **场景与 Job**（1.1） | 这句话管哪段工作、到哪个终态算完 |
| **主角色**（1.1） | 句子的主语与门槛变化：**谁**因此能做成什么 |
| **现状痛点**（1.1） | 效果那一段：**哪份难受消失**、拿什么验收 |
| **解决思路与 Non-Goals**（需求指令） | 目标的**边界**：能写到哪一层，不得越过指令声明的不做项 |

> 🛑 **不许把解决思路写进目标**：思路说的是"怎么做"（统一链路、平台主键、复用 WEB 口径），目标说的是"因此谁能做成什么"。思路交给 1.3 / 1.4，目标只留结果。

### 3. 输入里读不出来的怎么办：先补齐、后确认，**不中途停下来问**

| 缺什么 | 处理 | 标成什么 |
| :--- | :--- | :--- |
| 角色没写全 | 按需求指令里出现的操作者推定 | `【假设】角色：安全管理员` |
| 痛点没写明 | 从需求指令要求的字段与动作反推现状阻力 | `【假设】现状：逐台核对` |
| 度量基线没有 | 有数用数；无数改写成行为测法；仍无则标待定并给上线验法 | `【假设】基线待定，上线看 X` |
| 判定口径未定 | 给一个口径（不给备选） | `【假设】完成＝…` |

> 🛑 **执行纪律**：从 1.1 到 1.4 草图交付一路贯通，按上表补齐并标注，随交付物一起给，**由规划人员在草图那一次统一确认**。
> 🛑 **禁止提问的内容**：章节编号、模板 ID、组件名、字数、格式、字段要不要合并——这些是执行内部事，问了只是把决策成本转给用户。**自己定，标注出来，闸门处一次对齐。**

## 二、完成后判定（两条，任一不过即不合格）

| # | 判定 | 问句 | 通过标准 | 不合格处理 |
| :---: | :--- | :--- | :--- | :--- |
| **A** | 站在宽 Job 上 | 1.1 里这个场景的 Job，是"一段完整工作"还是"一次操作"？ | **按 1.1「Job 颗粒度」判据通过**（判据只在 1.1 定义：名字无操作词、有终态、只做一半有业务后果） | **退回 1.1 重拆 Job**，不在 1.2 硬写 |
| **B** | 写到工作终态 | 这句话到的是"某一步更顺"，还是"这类工作不再需要人这么做"？ | 说得出**谁因此不必再做什么**；不是把原来那串步骤加速 | 落在操作级 → 重写：终点往后推（配完 → 配完且发对了 → 这类事不用人盯） |

> 🛑 **判档只问两句，与"有没有量化"无关**：
> ① **这件事还需要原来的角色来做吗？**（工程师 → 普通用户／专家 → 新手／人 → 系统）
> ② **流程是被改写了，还是只被加速了？**（步骤被删掉、前置、合并 = 改写；同一串步骤更快 = 加速）
> 两句都还是"旧的"（原角色、原步骤）= 只到任务级；任一句被改 = 到工作级。
>
> 🛑 **不向用户追问"能不能再高一点"**：自己按上面两句往工作终态推，推不上去就退回 1.1，不把决策推回给用户。
> 📌 **别拿"效率提升"或"带了数字"当高档**：`4 次往返压到 1 屏` 还是那个人、那串步骤，只是加速；`0 基础也能配`、`无需主动巡查` 才是角色或流程被改。

## 三、写作顺序：先定维度，再定方向，最后成文

### 0. 四步

| 步 | 做什么 | 从哪取 | 得到什么 |
| :---: | :--- | :--- | :--- |
| **①** | **定位维度**：痛点是什么 → 用户被什么困住（**直接取 1.1 痛点矩阵的「用户困在」列**：烦 / 看不全 / 不敢信 / 说不清）→ 落到 1~2 个主打维度 | 1.1 痛点矩阵与现状基线 | 这条目标主打哪个维度，决定后面往哪写高 |
| **②** | **复述旅程**：这个场景从头到尾要干哪几件事、终态是什么 | 1.1 的场景 Job 与现状旅程（不重画图） | 目标要覆盖的那段完整工作 |
| **③** | **定高维方向**：如果不受现状机制约束，最希望用户到达什么状态/感受；再按需求指令的 Non-Goals 裁一刀 | 需求指令的立项目标与 Non-Goals | 一句话方向（不是交付句） |
| **④** | **成文**：按四段句法写成一句，契合①的维度，指标内嵌 | ①②③ | 交付句（过第二节判定） |

**①的维度池（15 个，只选 1~2 个主打，不逐维写）**：
快 / 高效 · 准 · 省 · 稳 · 简单 · 易用 · 品质感 · 信任感 · 专业 · 掌控感 · 降噪 / 聚焦 · 可解释 / 白盒化 · 无感 / 低摩擦 · 可见性 · 响应闭环

**痛点 → 困住方式 → 维度（同一痛点可能落到三个不同维度，别一律当"快"）**：

| 痛点长什么样 | 用户其实困在 | 落到维度 |
| :--- | :--- | :--- |
| 记录多、来源散、要一条条整理 | 烦 | 快 / 省 |
| 看不见有没有、看不全范围 | 看不全 | 可见性 |
| 不知道信哪条、不敢引用、怕算错 | 不敢信 | 信任 / 可解释 |
| 说不清依据、交账要解释 | 说不清 | 可解释 / 白盒化 |

> 📌 安全治理域最常漏的是四个方向：**可见性**（看不见 → 全貌可确认）、**研判**（碎片拼凑 → 快速定性）、**降噪**（被淹没 → 高置信优先）、**信任**（黑盒结论 → 依据可复核）。它们只用来判断"目标有没有写窄"，**不写成句子里的修饰词**——写成"一屏确认""高保真可视"就已经是界面方案。

```mermaid
graph LR
  A["① 痛点 → 困住方式 → 维度"] --> B["② 旅程：要干哪几件事、终态是什么"]
  B --> C["③ 高维方向：最期望用户到达什么状态（过 Non-Goals）"]
  C --> D["④ 成文：一句，契合维度，指标内嵌"]
  D --> E["过第二节判定"]
```

> 🛑 **③ 先写愿望、再裁边界**：愿望可以高（不用人比对、不用人巡查），但**越过 Non-Goals 的部分不写进句子**，只作为 1.3 / 1.4 的方向。

### 1. 成文规则

1. **落地写实、杜绝虚词**：
   * 严禁出现"大幅提升、更加清晰、体验升级、极致、全新"等无法证伪的形容词；
   * **具体 ≠ 界面具体**：目标要具体到**业务动作、角色门槛、场景载体、对标与效果**，**不写界面实现**——不写列 / 标签 / 弹窗 / 抽屉 / 按钮 / 入口层级 / 往返次数 / 一屏内。界面手段属于 1.4 与说明书的方案层，写进目标等于**先把答案定了，天花板就只剩界面优化**；
   * 判据：把目标里的界面名词全部删掉，句子仍然站得住、且能想象出角色怎么干活 = 目标；删完就空了 = 你写的是方案。
2. **严格固定句法（一句话，不分点、不加小标题）**：
   * 每条目标就一句：**`[谁（含门槛变化）现在能做成什么] ➔ [具体业务动作 / 载体] ➔ [效果：覆盖 / 时长 / 对标]`**
   * **"从 A 改成 B"只是内部判档的思考，不进句子**：反差通过"谁因此能做成什么"自己体现，不写脚手架开头。
   * 不得先写控件、按钮、页面改造，也不得先写收益口号或背景。
   * **这是与"能力清单"的分水岭**：`台账保持准确、异常浮出、清单同源` 是三条能力并列，像验收标准；`一线运维无需经验也能判断先处理哪几台` 才是目标——它说的是"谁因此能做成什么"。
3. **彻底剥离技术实现手段**：
   * 严禁堆砌底层技术原理（不写"通过大数据流式计算"、"基于机器学习算法"）；
   * 只描述用户在触点上**"能看到什么、能判断什么、能完成什么"**。
4. **度量指标直接融合嵌入**：
   * 将时间压缩、步数减少、准确率提升等客观数值直接融合成句，不单独分行孤立挂载。
5. **完整保留业务信息**：
   * 必须 100% 保留业务细节、数据、对标厂商、场景范围、角色、系统名称与约束条件，不得擅自删减。
6. **输出形态**：
   * **每个主场景一条**，写作 `**场景名称**：一句话体验目标。`，条数 = 1.1 主场景数，场景名逐字照抄 1.1；
   * 只出一版，**不出备选、不分档、不追加"验收方式"尾巴**；指标与测法嵌在同一句内；
   * 说明书 Part1 第 3 节落位时如需加粗短语，取该句开头 4~8 字，**不加新字、不改语序**；
   * 产物供 1.3 与说明书 Part1 第 3 节**原话引用**，因此在 1.2 就必须定稿。

> 🚦 **目标 / 方案分层（写完必过一遍）**
>
> | 层 | 该写什么 | 例子 |
> | :--- | :--- | :--- |
> | **目标**（本节） | 工作方式与结果发生什么变化 | 台账自己保持准确，人只在异常时被叫来 |
> | **方案**（1.4 / 说明书第 7 节） | 用什么界面与交互实现它 | 三态分列 + 独立标签 + 组合筛选 + 确认弹窗 |
>
> 目标里一旦出现"分列 / 标签 / 弹窗 / 抽屉 / 一屏内 / 往返 N 次"，就说明**目标被写成了方案**：读起来很具体，但天花板被锁死在界面层，1.3 只能拆出"看得清、点得准"这类小点子。

## 四、可衡量 ≠ 可量化

> 🛑 **常见误解**：以为每条目标都必须带百分比或时长。**要求是可衡量，不是可量化。**
> **可衡量 = 特定条件下、只有一个变量的可验证结果**：说清「谁、在什么条件下、做哪件事、看什么结果」，找个人一测就能判定真假。

| 类型 | 写法 | 能不能验收 |
| :--- | :--- | :--- |
| **有数**（需求指令已确认） | 一批终端从下达到全部到位，原来要人工逐台确认，现在人只处理未成功的少数几台 | ✅ 直接对数据 |
| **无数但有测法** | 一位没用过这套后台的运维，不看帮助文档，10 分钟内独立发完一批升级，并说出 3 台为什么没升上去 | ✅ 一测便知，无需百分比 |
| 无数也无测法 | "状态更清晰""操作更顺畅""体验明显提升" | ❌ 不可衡量，等于没写 |

> 📌 所以"**小白用户也能独立完成**"这类目标完全合格——它把变量收敛到一个人身上，换个人重测就能复核。**别为了凑数字硬编百分比**，那会把目标的画面感磨掉。
> 🛑 **无基线不写时间或百分比**：先说明基线从哪来；基线待补就标"待补"，或改写成动作数与行为测法。

## 五、范本与反例

**正例（用户已认可，保留原话）**

* **组网 1.0 体验**：批量部署实现极简开局上架，分支用户依托设备贴纸指引，插电插网即可完成设备上线；全场景统一配置能力支持灵活批量下发，在每段配置流程后置下发操作触点，保证配置至下发操作链路连贯无跳转，消除跨页面割裂操作。
* **GA 配置提效**：消减专业术语的理解成本，0 基础租户管理员也能独立完成任一加速规则配置，并保障多加速场景（内网应用/分支/SaaS 应用/自定义加速）下统一配置体验。
* **DEM 运维降本**：用户通过自然语言实现一句话报障，基于端到端的全链路拓扑可清晰定位分段异常点，逐层递进的推理链有条理可信任，大幅降低跨域盲排的心智负担；故障定位时长由传统数天压缩至 10 分钟以内，实现终端用户 0 打扰；报障场景效率可对标国际厂商 Cato、Zscaler。
* **终端台账**：终端台账随终端实际情况自动对齐，客户端注册即入账，版本与启停状态变化不再需要人工维护；掉线、被禁、版本落后的终端自己浮出来并说明原因，一线运维无需经验也能判断先处理哪几台；对资产、审计与上级交付的是同一份底账，口径不再需要人工解释。

> 📌 四条的高度都落在"谁因此能做成什么"，不靠对比句堆出来。其中「组网 1.0」「DEM 运维降本」成文较早，含界面动作（后置触点、跨页面、拓扑）与多分句、虚词（清晰定位、大幅降低），**只作水位参照，不照抄句式**——按第三节规则落地时压成一句、删掉界面词。

**反例**

| 写法 | 病在哪 |
| :--- | :--- |
| 大幅提升资产盘点体验，让台账更清晰、更易用。 | 口号，不可衡量，删掉形容词就空了 |
| 在资产列表新增筛选栏与批量操作按钮，编辑动作放进弹窗。 | 界面方案，天花板锁死在界面层 |
| 支持多源接入、支持统一标识、支持台账统计。 | 能力清单，只有系统做了什么，没有用户能做成什么 |

## 六、负向约束与反低级化红线

### 1. 禁用虚词清单
严禁使用无法证伪的空泛虚词：`提升体验`、`优化视觉`、`变得更好`、`更加便捷`、`更加智能`、`更加友好`。

### 2. 严禁反模式（仅适用于安全类需求）
* 🛑 **严禁安全剧场/花哨炫技**：不得把体验目标写成无实际研判价值的 3D 拓扑、酷炫大屏、动效堆砌或满屏无意义跳动数字；
* 🛑 **严禁脱离上下文告警**：不得只描述"提示风险"，必须说明如何呈现风险上下文、判断依据、影响面与处置建议；
* 🛑 **严禁黑盒式结论**：不得只写"系统自动判定高危"，必须体现用户可理解、可复核、可追溯、可采信；
* 🛑 **严禁以牺牲业务效率换取安全**：不得把频繁打断、过度拦截、复杂审批包装成体验目标。

### 3. 反低级化约束（重要）
严禁将体验目标写成：
* ❌ 单个页面、单个按钮、单个字段或单个操作步骤的局部优化；
* ❌ 三个互不关联的小功能点凑数；
* ❌ 口语化流水账执行描述（如"用户可以配置规则"、"用户可以查看结果"）；
* ❌ 只描述系统做了什么，不说明用户能力发生什么跃迁；
* ❌ 只描述操作变少，不说明业务判断、结果确定性或风险掌控如何变化。
* 🛑 **不许出现界面控件**（列 / 标签 / 弹窗 / 抽屉 / 按钮 / 一屏内 / 往返次数）——写到了就是方案，不是目标。
* 🛑 **无基线不写时间或百分比**：先说明基线从哪来；基线待补就标"待补"，或改写成动作数与行为测法。
* **铁律：必须聚焦同一个核心 Job，句子里读得出"角色或流程被改写"这一层跃迁，而不是把原步骤写快。**
