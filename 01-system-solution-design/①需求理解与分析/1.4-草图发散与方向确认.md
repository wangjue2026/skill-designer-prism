# 1.4 草图发散与方向确认 (Sketch Divergence & Direction Confirmation)

> 💡 **中枢定位**：
> 本文档承接 [1.3 体验突破点拆解](1.3-体验突破点拆解.md)，是【方案系统设计主线】Part1 的**收尾环节，也是整条主线上唯一的分岔点**。
> * 1.3 定的是"**在哪破、怎么破，摆出几档打法**"；
> * 本步定的是"**画出来是几个样子、走哪一个**"。
>
> ⚠️ **这一步的性质是"出方向"，不是"出方案"。** 草图不是线框图，它只回答一件事：**同一批突破点，能摆成几种结构完全不同的页面形态，每种形态里人还出多少力。**

> 🛑 **阶段铁律**：
> 1. **草图不是线框图**：只画**关键框架与布局占位**，不排字段、不调间距、不定组件、不写 Token。细则进不了草图，进了就变线框（那是 4.1 的活）。
> 2. **一档一套、必须成套**：一个方向要**整套页面**（不只画一屏），否则看不出这个方向能不能站住——很多方向单屏好看，连起来就断了。
> 3. **非设计点允许占位**：不承载突破点的区域，用一个灰块 + 一句说明带过（"此处沿用现有列表页，本次不动"），**不许为了显得完整而随手画满**。
> 4. **每个方向必须能回答"它对应哪几处突破点"**：对不上的草图是自嗨，退回重画。
> 5. **两个方案必须真的岔开**：如果只是"把侧栏换成顶部栏"，那是一个方案的变体，不叫两个方案。
> 6. **到这里必须停（默认不可跳）**：草图出完即停在确认闸门，**未获方案选定，严禁进入页面清单、模板选型、线框图与任何代码**。**停下之前必须先过草图门禁**（`bash tools/gate-ex.sh 1.4 _output/<业务名>/草图-<业务名>.html` 拿到全绿：结构 5 条 + 文案 7 条，**文案机检不合格同样不许交付**），带着硬错给用户看，等于让他替你挑按钮位置。**唯一例外**：用户**明确说出**"跳过草图 / 不用给我看草图"时，可越过闸门并**默认以方案一（高水位）执行**；用户只说"给我出说明书"不算跳过，见第七节铁律。
> 7. **草图守"结构级规范"，不守"精度级规范"**：草图必须与线框**同源**——主按钮用主题蓝、主按钮在左取消在右、抽屉/弹窗/表格不混用、页面分区骨架一致。**否则草图到线框会出现"我选的方案被改了"的断裂感**。但精度级（精确像素、字段名、星号占位、图标、动效）**一律不管**，管了草图就变线框。
>
> 🛑 **一句话分界**：**会改变"结构长什么样"的规范要跟；只改变"做得多精细"的规范不跟。**
> * **必须跟**（结构级，错了线框就变形）：主按钮颜色与左右顺序、**页脚按钮对齐（抽屉贴左 / 弹窗贴右）**、容器形态（抽屉/弹窗/整页）、页面分区骨架、内容承载方式（表格/卡片流/表单）；
> * **不跟**（精度级，跟了用户就开始挑细节）：精确像素、字段名与列名、星号占位对齐、图标、动效、Token 细节。
>
> 🛑 **另一条边界**：线框图**不能因为"草图这样画的"就沿用草图的松散画法**——草图继承的是**分区与主结构**，不是它的精度。**继承结构，重做精度。**

## 零、这一步产出什么

| 项 | 内容 |
| :--- | :--- |
| **输入** | ① 主要场景清单 S1~Sn（1.1）② 各场景体验目标与指标（1.2）③ 各场景突破点 + 分档点子（1.3） |
| **产出** | ① **2 套方案草图**（方案一 / 方案二），每套 = **一条走法 × 一组档位** + 整体设计说明 + 设计思考点 + 逐页草图与逐条说明<br>② **用户选定结果**（选高水位时含目标/指标变更授权；确认后留档，作为下游唯一入口） |
| **内部留档（不交给用户）** | 档位组合 / 突破点落点 / 动作覆盖表 / 五段代价 / 目标与指标变更 |

> 📌 **一句话**：基于需求场景，把 1.3 的点子按**走法 × 档位**拼成两套，用**不懂业务的人也读得懂**的写法摆出来，让人一句话就能选。

### 🛑 四条输出铁律（最重要，先看这）

| # | 铁律 | 反面（实测犯过） |
| :---: | :--- | :--- |
| **1** | **只给 2 套**，两套的**走法与档位都要不同**；高水位还要过**实质自检**（≥2 处档位差含主战场页、说得出"人少干了哪件事"） | 一上来给 3 个方向 + 全量信息，**选择过多、信息过载**；或两套只是档位滑动，成了**拼盘**；或贴了"高水位"却看不出强在哪 |
| **2** | **不画常规版**，从**创新版 / 优化版**起画 | 把"最没设计含量"的那套也摆上台 |
| **3** | **图的框里只放内容，不放解释；解释一律写在草图正下方**——图上打标号，图下按标号逐条写"做法 + 为什么" | ①框里塞解释句挡着看结构；②**只有编号、图下没有说明**，用户看不懂这处在干嘛 |
| **4** | **所有文案必须站在用户视角**：说清"你会看到什么、你能做什么、做完会怎样"；**不写机制名、不写内部编号、不造词** | 「最小处理集合」「采信」「回执」「四组队列」「B2」——用户读不懂，也讲不出去 |

> 📌 **为什么是 2 套不是 3 套**：三套让用户进入"比较模式"，注意力耗在分辨差异上；两套进入"选择模式"，一句话就能定。**高水位那套放第一个，用一句实话说明它多解决什么、要多付什么。**
> 📌 **为什么常规版不画**：常规版是"别人怎么做我们怎么做"，它**不需要被选择，只需要被满足**——它是优化版/创新版的地基，画出来只会稀释重点。**如果两套都还停在基线上，说明这需求没设计空间，直说。**
> 📌 **铁律 3 与铁律 4 的关系**：**框里不解释，但图下必须解释。** 标号是"图"与"说明"之间的钩子，不是装饰；没有图下说明的标号等于没说。

### 交出去的是什么：一份单文件 HTML（页头 + 对比表 + 两个 tab）

**结论：`页头（页面总数 + 清单）→ 两套方案对比表 → [方案一 tab | 方案二 tab]`。**

| 内容 | 要不要 | 说明 |
| :--- | :---: | :--- |
| 场景名、体验目标、突破点清单、档位上限 | ❌ **不放顶部** | 这些**已经有共识**（1.1~1.3 都过过了），再摆一遍是重复劳动，还挡着看图 |
| 方案标题句（如"系统出草案，人只改差异"） | ❌ **不要** | **方案只叫「方案一」「方案二」**；这套方案是什么、解决什么，写进对比表的「整体设计说明」 |
| 水位徽标 / 推荐标 / 吸顶差异条 | ❌ **不要** | 水位差与差异由对比表承担，不再靠徽标和"3 条差异" |
| **⓪ 页头标题 + 一行小字** | ✅ | `需求草图示意` + "仅用于思路对齐，不涉及详细设计" |
| **① 本次需求一共 N 个页面** | ✅ | **放最上面**；紧跟一张页面清单（见第三节） |
| **② 两套方案对比表** | ✅ | 整体设计说明（含代价）+ 各自的设计思考点，**表格形式** |
| **③ 切换条（吸顶）** | ✅ | 只有两个：`方案一` ｜ `方案二`，点击切换 |
| **④ tab 内：按页面分块** | ✅ | 每页 = 草图（带标号）+ 图下逐条说明（做法 + 为什么） |

> 🛑 **不要前置一堆元信息**：用户点开文件，第一眼应该看到**页面规模和页面清单**，不是"场景 S1 / 体验目标 / 档位上限"这种台账。
> 🛑 **但对比表必须有**：两套方案的取舍要能并排读完；只给图、不给"两套各在想什么"，用户只能凭感觉选。
> 📌 **页面清单必须有**：否则用户不知道"这个需求一共几个页面、两个方案差在哪些页面"。

### 每一套方案的结构

```
方案一（tab）
├── P0 页面名（形态 · 主战场?）
│   ├── 草图：区块右上角打标号 ① ② ③（同一组内容只打一个）
│   └── 图下逐条：① 做法：…… 为什么：……
├── P1 页面名（形态）
│   └── …
└── P5 页面名（形态）
    └── 与方案一相同 → 一行交代，不重复画
```

> 📌 **设计说明必须回答"这个想法从哪来"**：每条思考点都要指回现状里的一个具体卡点（用户原话或 1.1 的卡点），**不写"因为这个方案更好"**。

## 一、先分清三张图（最容易混）

| 图 | 在哪一步 | 回答什么 | 精度 | 谁看 |
| :--- | :--- | :--- | :--- | :--- |
| **现状旅程图** | 1.1 | 现在人怎么干、卡在哪 | 流程级 | 内部 |
| **草图** | **1.4（本步）** | **这事有几种摆法，走哪种** | **布局占位级** | **规划人员（要选）** |
| **实现线框图** | 4.1 / 5.0 | 选定那种摆法，具体怎么落地 | 组件级 | 开发 / 评审 |

> 🛑 **混用的后果**：草图做成线框 → 用户在细节上纠缠，反而看不出方向差异；线框图做得像草图 → 开发看不懂，实现走偏。**两者精度必须拉开。**

## 二、怎么出方案（先岔走法、再配档位、最后拼成 2 套）

一套方案不是凭空想的，也不是"挑一组点子"——它是**一条走法 × 一组档位**。

> 🧭 **为什么要把这根轴说清**：只按走法分两套（两套水位一样高），最值钱的创新级点子永远进不了方案主体，只能被降档成一行注记；只按水位分两套（走法一样），得到的是两套精细度不同的**拼盘**，用户看的还是同一件事。**两维都得有差，才是两套方案。**

### 思考顺序：先岔走法，再给每条走法配档位，最后按二维挑两套

```text
① 按场景找岔口（同一件事，页面骨架/分工可以怎么歪）
        ↓ 一般能想出 3~4 种
② 给每条走法配一组档位（越高越要付代价，见后文"档位构成硬要求"）
        ↓
③ 按二维挑两套：走法不同 + 水位不同
        ↓
④ 常规版不画（它只是这两套的地基）
```

### ① 岔口在哪：五个维度（够用了，不必更多）

| 分岔维度 | 可以怎么摆 | 举例（合规检测任务） |
| :--- | :--- | :--- |
| **谁先动** | 人找对象 / 系统推出该处理的 / 系统判完人只确认 | 人自己选范围圈条件 vs 系统按资产画像出草案 |
| **任务放在哪** | 独立页 / 抽屉 / 弹窗 / 内嵌在原页 | 新建任务独立成页 vs 抽屉内配完即走 |
| **主线纵向还是横向** | 列表 → 详情 → 操作（纵向）／ 工作台一屏办完（横向） | 先选任务再看结果 vs 直接进"待处理"工作台 |
| **一屏管几件事** | 单任务单屏 / 多任务合屏 / 一屏管一类对象 | 一个任务一页 vs 一屏管所有任务 + 结果 |
| **改动落在哪里** | 改现有页面 / 新增页 / 重构导航 | 在现有列表上加能力 vs 新开一个运营工作台 |

> 📌 **最常出创新版的是第一个维度（谁先动）**。其他四个维度多半只能变"摆法"，变不了"分工"。
> 📌 **判一句**：把两个方案并排念一遍"用户第一步看到什么、第二步做什么"——**两步都一样，就不是两个方案**。

### ② 配档位：给每条走法配"一组"档位，不是逐处随手取一档

档位来自 1.3 的四档点子表，但**取法不是逐处自由挑**，而是按水位成套配：

| 位置 | 档位构成硬要求 | 为什么这么定 |
| :--- | :--- | :--- |
| **方案一 · 高水位** | **≥2 处创新版**，其余不得低于优化版；**不许出现常规版** | 创新档才是"换人机分工"；没有它，这套只是"做得更好的优化版" |
| **方案二 · 稳水位** | **全部落在优化版**，最多允许 1 处创新版（该处方案一须是另一种更彻底的形态）；**不许出现常规版** | 优化版是"同一个做法做到最好"，不是没设计；但判断仍由人下，所以不给创新 |
| **同一处突破点** | 两套**不得同档**；同档的标"两案相同"，不再画 | 同档不贡献差异，摆上去只增篇幅 |

> 🛑 **档位差的背后是代价差**：同一处从常规版走到优化版，通常只是信息组织与路径的重排；从优化版走到创新版，通常意味着后端要能算、系统要能自动判，或者人机分工要改。**水位差如果对不上代价差，说明档位是硬凑的。**
> ⚠️ **创新档进方案，必须同时给两行**：`换掉了哪一步人机分工` / `防误伤怎么办`。两行缺一行，这处降回优化版——**这是防止把"追覆盖率→狂下发→断业务"这类风险藏在一个漂亮方案里。**

### ③ 拼成 2 套：走法与档位，两维都要有差

```text
① 五岔口出 3~4 条走法
② 每条走法配一组档位（按上面②的硬要求）
        ↓
③ 挑两条：走法不同 + 水位不同
      走法不同、水位相同 → 其中一条重新配档，或砍掉
      走法相同、水位不同 → 判为拼盘，退回 ① 重想走法
        ↓
④ 同一处 Bx 两套同档 → 标"两案相同"，不画
⑤ 每套出一行档位组合：B1 创新 / B2 创新 / B3 优化 …
```

| 位置 | 怎么挑 | 在文里怎么表达 |
| :--- | :--- | :--- |
| **方案一（高水位）** | 走法上敢动人机分工，档位上至少 2 处创新 | 标题缀 `高水位`，紧跟一句"多解决什么、要多付什么" |
| **方案二（稳水位）** | 走法上阻力最小、改动最少，档位全部落在优化版 | 标题缀 `稳水位`，多写一句"适合什么情况下选它" |

> 🛑 **不凑第三个**：如果只能想出两套像样的，就给两套。**硬凑的第三套，一眼就看得出是凑的，反而降低可信度。**
> 🛑 **两个都不满意怎么办**：那就是回第二节①重岔走法，不是往回收一个常规版垫底。
> 🔎 **判"拼盘"只需一句**：把两套的"第一步看到什么、第二步做什么"各念一遍——**两步都一样、只是精细度不同，就是拼盘，不是两套方案。**

### ④ 特例：走法真的岔不开时

如果需求很实、走法没什么可岔的（比如"给现有列表加个批量处置"），允许**两套共用同一条走法，只在档位上分**：

| 位置 | 要求 |
| :--- | :--- |
| 方案一 | 至少 2 处创新版，并在依据里写明"走法无分岔，本套靠档位拉开" |
| 方案二 | 全部优化版 |
| 必须补一句 | **"这件事在创新档下会变成什么样"**——哪怕不画，也要写 |

> 📌 **为什么要补那一句**：**"结构只有一屏"不等于"分工不能变"**。批量处置做得再顺，也可能本来就该由系统自动执行——把这条特例当成"这需求没有创新空间"的免死牌，就会漏掉真正的创新档。
> **这时更要严格不画常规版**——否则整份文件就只剩一张谁都想到的图。

### ⑤ 高水位的"高"要看得见，不能只是个标签

> 📌 **用户判断"这套有没有东西"，不看档位名，只看三个地方。**

| 感知点 | 高水位必须不同在哪 | 只是"精细一点"不算 |
| :--- | :--- | :--- |
| **第一眼（首屏）** | 多一个"结论 / 该办什么"区，或少一个"先选条件"的动作 | 同一屏里标签更全、按钮更顺 |
| **步数** | 少一次跳转 / 少一次判断 / 少一次自己去找去查 | 同一条路径上少点两下 |
| **结果呈现** | 直接给结论 + 依据 + 下一步 | 原始数据摆得更整齐 |

**两条硬要求（达不到就不是高水位）**：

1. **≥2 处 `Bx` 与方案二不同档，且至少 1 处落在主战场页**（用户花时间最多、操作最重的那一页）。只在边角页发力（比如列表顶部加个统计条）不算。
2. **说得出"用户少干了哪一件具体的事"**：一句话、动词在手——"不用自己圈范围""不用逐个看哪台不合规""不用等跑完再回来看"。**说不出这件具体的事，这套就只是优化版换了张皮。**

> 🛑 **"高"不等于"多"**：创新档往往界面更空（系统把活接走了，见 §四）。**不许用"页面更多 / 组件更多 / 区块更多"来证高**，只许用"人少干了什么"。

**天花板真的低时（需求小 / 目标只到优化版），两种正确处置**：

| 情况 | 正确处置 |
| :--- | :--- |
| **天花板低，但仍有档位空间** | **方案一取"顶格档"、方案二取"顶格下一档"**，不要两套都停在中段。水位差可以只有 1 档，但必须是**最高的相邻两档**——这是"尽量拉开"的底线 |
| 创新档在本需求里不成立，或代价明显大于收益 | **不许贴"高水位"标签**：改叫 `方案一 · 上限版`，并在选择区写明"本需求最高到 [优化版]，原因是 [目标只要求… / 创新依赖的能力本期没有]" |
| 两套在第一眼、步数、结果三处都一样 | **不出两套**：只出一套 + 一页"备选档位"，并说明为什么岔不开——**硬造的高水位比只给一套更伤信任** |

> 🔁 **先回 1.3 找料，别先降低标准**：高水位没料时，按顺序查三处——① 点子是不是只摊到了优化档（回 1.3 第 3 步换维度重摊）；② 入口 2（工作类型经验）是不是漏扫了；③ 某处创新档是不是因为"怕代价"被自己划掉了。**三处都查过仍无料，才认定天花板低。**

**三种"假高"，一眼识破**：

| 假高 | 长什么样 | 为什么假 |
| :--- | :--- | :--- |
| **换容器** | 抽屉改整页、列表改成分栏 | 人还得自己判断、自己找，只是换了个壳 |
| **加装饰** | 顶部加一排"智能概览"卡片 | 界面多了东西，人没少干活 |
| **档位虚标** | 两处优化版合并说成一处创新版 | 档位是标出来的，不是做出来的 |

> 🔎 **一句话判据**：**高水位 = 用户少干了一件具体的事。** 说不出这件具体的事，就不是高。

## 三、先定全部页面清单，再画草图（本步交付的第一块）

> 🎯 **这是本步最容易卡住的一问**：不给页面清单，草图怎么知道画到哪个页面里？给了页面清单，不就等于结构已经定了、没得岔了？
>
> **答案：先有"页面草图清单"，后有"正式页面清单"。前者是本步产物，后者是 4.1 产物。**

| 谁定的 | 定的是什么 | 精度 | 能不能改 |
| :--- | :--- | :--- | :--- |
| **本步（1.4）★ 先做** | **页面草图清单**：这个需求一共涉及哪几个页面 / 视图 / 弹层、各自叫什么、管什么、在两个方案里有没有差异 | 粗——只到"有这么个页面、它管什么" | 随方案一起改 |
| **4.1 ★ 后做** | **正式页面清单**：页面编号 `Page-0x`、交互形态、模板 ID、承接主场景、来源草图 | 细——到组件与 Token | **原则上不改**；要改必须回本步重确认 |

### 为什么清单要给用户看（实测修正）

> 📌 **第一版把清单当内部台账藏起来了，这是错的。** 用户的原话：**"用户看到全貌会更清晰——原来是有两种方案、差异是什么，以及本次我的需求大概有多少个页面。"**

清单摆在文件最开头，一次回答三个问题：

| 用户想知道 | 清单里哪一列回答 |
| :--- | :--- |
| 本次需求一共几个页面 | 第一列，整个表有几行 |
| 每个页面干什么的 | 「这一页管什么」列 |
| 两个方案差在哪 | 「两套方案」列（**有差异 / 差异最大 / 两套相同**）——这一列直接决定后面要不要重复画 |

### 清单格式（交付物第一块，开头就放）

**只写用户看得懂的 5 列，不放档位与突破点编号**（那些进内部留档）：

| 页面 | 名称 | 形式 | 这一页管什么 | 两套方案 |
| :---: | :--- | :--- | :--- | :--- |
| P1 | 合规基线检测 | 列表主页 | 看任务与最近一轮结果，进新建 | **有差异**：首屏给不给结论 |
| P2 | 新建检测任务 | 右侧抽屉 | 配规则、看会影响谁、确定下发 | **差异最大**：谁来决定查什么 |
| P3 | 任务执行与结果 | 详情页 | 看谁收到、谁不合规、就地补发 | 两套相同 |
| P4 | 未收到终端清单 | 抽屉 | 查为什么没收到，就地补发 | 两套相同 |
| P5 | 规则模板库 | 抽屉 | 选一套现成规则、套用改差异 | **有差异**：方案二不涉及 |

> 🆕 **新模块必须单列 `P0` 接入页**：从 0 台开始的产品，第一屏不是"空表格"，而是"怎么把对象弄进来"。**接入途径按实际情况列**（很多产品只有普通导入，不要凭空补扫描/同步/分发）；`P0` 通常两套相同。
> ✅ **对齐检查（内部留档里做，不写在清单上）**：清单必须把 1.3 的每一处 `Bx` 都找到落点页面，**一个都不能漏**。漏了就是"这处突破点无处落地"——要么补页面，要么写明"本期不做 + 原因"。

#### 定稿清单前必交：动作覆盖表（防"只画了一条主线"）

> 🛑 **实测病**：需求写了"安装升级（三类组件）/ 卸载 / 解绑 / 批量编辑 / 基础配置"五个动作域，草图上只沿着"安装升级"画，其余四个动作**静默消失**。规划人员一看就知道"这不是我要的"。
> 📌 **PRD 里的"动作清单"不是示意，是验收项。** 每一个动作都要有页面落点，落不了的必须写"本期不做 + 原因"。

| 业务对象 | 动作 / 状态 | 落在哪个页面 | 本期是否做 | 备注 |
| :--- | :--- | :--- | :---: | :--- |
| [终端] | 安装（底座 / 保护AI端 / Hook 分别安装） | P3 | 是 | 三类组件可分别选 |
| [终端] | 升级（同上三类） | P3 | 是 | — |
| [终端] | 卸载 | P2 / P3 | 是 | 高危，需影响确认 |
| [终端] | 解绑 | P2 / P3 | 是 | 高危，需影响确认 |
| [终端] | 批量编辑 | P1 | **否** | 原因：本期只做单条编辑 |
| [终端] | 基础配置（自启动 / 防卸载） | P2 | 是 | — |
| [终端] | 导入 | P5 | 是 | — |
| [终端] | 打标签 / 导出 | P1 | 是 | — |

> 🛑 **字段清单 ≠ 界面清单**：PRD 给的字段是**信息备选池**，不是列清单。哪些上主表、哪些进详情、哪些合并成一列，由"这页要办成什么事"决定；但**每一项都要能说出它去了哪**（主表 / 详情 / 不展示 + 原因）。
> 🛑 **表里出现"本期不做"的，必须在交付时向规划人员口头点一次**，不许埋在表里。
> 🛑 **红线**：本步清单**只写"名称 + 形态 + 职责 + 差异类型 + 档位名"**。一旦开始写模板 ID（`page-form-drawer`）、组件名（`IxDrawer`）、字段清单，就已经跑到 4.1 去了，**回退**。
> 📌 **一句话**：**1.4 定"有几屏、各管什么、哪里不一样"，4.1 定"每屏用什么模板、什么组件"。**

### 两套方案怎么摆：用 tab 左右切换，不许上下堆

> 🛑 **相同页不再重复画（2026-10-23 修正）**：旧规则要求"共性页照画、标两方案相同"。实测代价是**近一半篇幅在重复**，用户反而找不到重点。现规则：**相同页在各自的 tab 里留一个占位条**，一行写"P5 ×××：与方案一相同"，保留页面编号与名称，**不画图**。

```text
页头：需求草图示意 + 本次需求一共 N 个页面 + 页面清单（全局唯一）
对比表：方案一 / 方案二 的整体设计说明（含代价）+ 各自的设计思考点
切换条（吸顶）：[ 方案一 ]  [ 方案二 ]
  ├─ 方案一 tab：P0 → P1 → …（每页：草图 + 图下标号说明）
  └─ 方案二 tab：同上，页面顺序与方案一一致
```

| # | 铁律 | 为什么 |
| :---: | :--- | :--- |
| **1** | 每个 tab 内按页面顺序排**完整链路**（进入 → 操作 → 看到结果），不许"见共用页面"跳转 | 跳转就是断裂：用户看到"见下方"就得滚出去，回来还得重新定位 |
| **2** | **每页草图下必须有标号说明**，一个标号一段，写"做法 + 为什么" | 只有图、没有说明，用户只能猜；这是本次最核心的修正 |
| **3** | 相同页用**占位条**交代（页面编号 + 名称 + 一句"与方案一相同"），**不重复画** | 重复画占篇幅、稀释重点；一句话就能交代清楚 |
| **4** | 页面清单**只出现一次**（tab 之上），每行标 `有差异 / 差异最大 / 两套相同` | 清单是全局全貌，属于"选之前"要看的 |
| **5** | 两套的页面**顺序与编号一致**，同一页在两套里位置相同 | 左右切换时视线不跳，才能对照 |
| **6** | 新模块的两态（刚接入 / 有内容）**两套都要有交代** | 只给一套画两态，另一套显得薄，对比不公平 |
| **7** | 有差异的页，差异用**一句人话**写清（`方案一：系统先给建议，人只确认` / `方案二：人自己选范围`） | 水位差常常只差"默认空的还是满的"，不写字看不出来 |

> 📌 **优先级**：**能看懂 > 能对比 > 省篇幅。** 前两者冲突时，宁可文件变长。
> 🛑 **不许用"相同页"当省事的借口**：占位条必须带页面编号和名称，让用户知道"这一页存在、只是两套一样"，不许整块消失。

## 四、每个方案要交什么

一个方案 = **三个必填件**，缺一个就算没交：

| # | 必填件 | 给谁看 |
| :---: | :--- | :--- |
| 1 | **对比表里的两段**：整体设计说明（含代价）+ 各自的设计思考点 | 看方向的人（30 秒） |
| 2 | **逐页草图**（按页面成套，带标号） | 想看清结构的人 |
| 3 | **图下标号说明**（每条标号一段：做法 + 为什么） | 要拿去讲给别人听的人 |

> 档位组合、突破点落点、五段代价明细、动作覆盖表 → **进内部留档**，不占交付物版面。

### 1. 草图本体（按页面成套）

- **画法**：用与现有系统一致的**线框原语**（灰块 / 灰线 / 占位条），保持"骨架感"；
- **必须画出来的**：页面整体分区、主内容区放什么类型的东西（列表 / 卡片流 / 拓扑 / 表单 / 结论区）、关键操作位置、跨页的入口关系；
- **必须标出来的**：**设计点**——用**标号**（①②③…）标在区块**右上角**，**同一组内容用虚线框圈住、只打一个标号**；标号必须与图下说明一一对应；
- **可以不画的**：字段明细、列的具体名称、组件样式、颜色、间距、图标；
- **非设计点区域**：灰块 + 一句 `此处沿用现有 XX，本次不动`。

> 🛑 **不许出现 `B1 / B2` 这类经验编号**：那是 1.3 的内部指针，用户看不懂。编号只用于"图 ↔ 图下说明"的对应，**图下说明里也不写 Bx**。

#### 点子怎么变成图上的一个块（从 1.3 到草图元素的转译）

> 🎯 **这是最容易断的一环**：1.3 给的是"提交前给影响预览"，这是个**句子**；草图上要出现的是个**方块**。中间缺一步转译，结果就是"点子表很漂亮，草图上看不出用没用"。

转译只有一条规则：**问这句点子在界面上"让人多看见了什么 / 少做了什么"，那个东西就是一个占位块。**

| 1.3 的点子（句子） | 问：界面上多了什么？ | 草图里画成 | 标号 |
| :--- | :--- | :--- | :--- |
| 提交前给影响预览：哪些会被命中、哪些会被自动阻断 | 多了一个"后果说明区" | 抽屉底部一个区块：三个数字（将受检 / 离线 / 可检）+ 一行提示 | `①` |
| 按"防病毒 / 防泄密 / 防外联"分组预置，勾选即填完 | 多了"一组可勾的项" | 一个区块：三行标签 + 展开入口 | `②` |
| 系统按资产画像自动出整套基线 | 多了"系统已填好的内容" | 同上区块，但**默认是满的**，并带"已预置 12 项"字样 | `②`（同一组，共用标号） |
| 规则组独立成模板，可命名 | 多了"来源与保存"入口 | 表单顶部一行：来源标签 + "保存为新模板"链接 | `③` |
| 三态进度 + 失败终端可查 | 多了"三个数字并排" | 详情页顶部三栏数字卡 | `④` |

> 📌 **同一处点子在不同档位下，画出来的差别就在"是空的还是满的""是人填还是系统填"**——这是草图上唯一要表达的档位差异，不靠颜色、不靠组件。
> 🛑 **转译不出来 = 这条点子是"感觉"不是"做法"**，退回 1.3 重写：说不出它在界面上让人多看见什么，它就落不了地。

#### 创新档的区域可以画得很空（唯一允许"留白"的情况）

系统把活接走了，界面上本来就只剩"确认 / 状态 / 结果"。**这是对的，不要因为"怕看起来没设计"就把内容填满——一填就退回优化版。**

| 做法 | 具体要求 |
| :--- | :--- |
| 区域形态 | 极简态 / 空态即可（一行状态 + 一个确认 / 一个结果列表） |
| 框里写什么 | 内容标题照写（如 `系统自动判定结果` / `本轮到期待确认`），不写解释 |
| 必须交代 | 在**图下标号说明**里写明"**因为系统接管了 X，此屏只剩确认**"——否则用户会以为这页没做完 |

> 🛑 **不要用"填满"来证明设计存在**：创新档的价值在于人少干活，图上看起来"没东西"恰恰是它的证据。**空得有理，比填得满更好看。**

### 1.5 每一页出现的顺序，要能读出"人怎么走"

一套草图不只是几张图，**图的排列顺序本身就是设计**：

```
P1 列表（人从这进） → P2 抽屉（就地配，不跳页） → 回 P1（看到状态变了） → P3 详情（点进去看结果）
```

- 排列要能回答一句：**"用户第一步看到什么、第二步做什么、什么时候知道自己成了"**；
- 如果两个方向的排列顺序一样，**它们大概率不是两个方向**（回第二节第一层重岔）；
- 抽屉 / 弹窗类页面，**必须露出背后的承载页轮廓**（灰化处理），否则"就地闭环、不跳页"这个最大的卖点在图上是看不出来的。

### 2. 图下标号说明（每条标号一段，最重要）

固定两段，**缺任一段都不算交**：

```
① 做法：这处长什么样（一句话）
   为什么：针对现状里的哪个问题（一句话，指回 1.1 的卡点或用户原话）
```

- 好例子：*"② 做法：四类问题各占一格，格子里写明判定标准。为什么：这四种状态容易混，混了就会把'已安装'当成'已经在管'。"*
- 坏例子：*"② 做法：使用四象限布局，提升信息密度。"*（没有为什么，也没有取舍）

**判据**：把这段念给没看过需求的人，他能说出"**这处让我多看见什么 / 少做什么**"。说不出，重写。

> 🛑 **不许写**：`B1 / B2` 等经验编号、机制名（如"最小处理集合""四态并列"——要用人的话说"先做哪几件""四种状态分开写"）、"提升体验 / 更清晰 / 更高效"这类形容词。
> 🛑 **不许图和说明对不上**：图上有几个标号，图下就必须有几段；标号不许只当装饰。

### 3. 整体设计说明（对比表第一行，每套一段）

格式固定：**`把「<现在怎么做>」变成「<改成怎么做>」。代价：<谁要跟着变、每轮多花/省多少>。`**

- 3~4 句，≤120 字，一段说完；
- **代价必须写在同一段末尾**，不许另起一块、不许用小字灰色带过；
- 「现在怎么做」用用户的原话或 1.1 的卡点原文，不写"现状存在一定问题"。

> 🛑 **没有代价那一句，"高水位"就成了"高级版"**：用户会默认它更好，闭眼选，上线才发现要改流程、改指标。**水位差必须折成代价差。**

### 4. 设计思考点（对比表格，两套各列各的）

| 要求 | 说明 |
| :--- | :--- |
| 条数 | **不要求两套一致**，各说各的；硬凑维度会让话说得别扭 |
| 每条内容 | 思考点（用户视角一句话）+ 为什么这么想（指回具体卡点） |
| 取舍怎么标 | 属于取舍的（如"不改分工，所以不派单"）**写明"取舍"**，不许包装成优点 |
| 来源怎么标 | 「为什么」一栏必须落到 1.1 的卡点或用户原话上，**不写"因为这样更好"** |

### 5. 成立前提与代价明细（内部留档，不交给用户）

一句话说清"这个方案成立要靠什么"：*要靠资产画像准确 / 要靠后端能给出影响面预估 / 要靠预置库有人维护*。**前提不成立的方案，不能当作可选项摆给用户。**

代价明细固定五段（对比表里只留一句总述，明细留档备查）：

| 段 | 写什么 |
| :--- | :--- |
| 改动范围 | 动几个页面 / 要不要动流程与角色 |
| 影响面 | 谁要跟着变（运维习惯、下游系统、口径） |
| 上线风险 | 主要靠什么兜底（先小范围试、可回滚） |
| 工作量档 | 大 / 中 / 小（粗估即可，不给人天） |
| **每轮多花多少人工** | **每次/每轮要多几步操作、多花多少时间**。**这一行最容易被漏，也最影响用户选择** |

> 🛑 **只算"项目成本"、不算"用户的日常成本"**：稳水位方案往往改动小、风险低，但把活儿留给了人。**不写这一行，等于把最大的代价藏起来。**

## 五、草图的画法标准（答疑：画成什么样算合格）

> 📌 **为什么要标准化**：不标准就会出现两种失控——**画太细**（用户开始挑颜色和间距，方向讨论变成细节讨论）和**画太粗**（用户看不出差异，只能说"都行"）。标准的作用是**把草图钉在"刚好看得出结构差异、又看不出实现细节"那一格**。

### 1. 视觉规格（同一套灰块语汇，**结构级规范跟随、精度级不管**）

草图可以借用 `.wf-*` 里的**灰块 / 容器轮廓 / 占位条**这几个视觉语汇（省得另造一套观感）。但借用分两种，必须分清：

| 借用类型 | 例子 | 草图能不能用 | 原因 |
| :--- | :--- | :---: | :--- |
| **面块语汇**（只表达"这里有一块内容"） | `wf-card` `wf-row` `wf-shell` `wf-label` `wf-table` | ✅ 用 | 与规范无关，纯粹是画法 |
| **规范结构件**（自带规范语义） | `wf-form-item` `wf-form-label` `req` 星号占位 | ❌ 不用 | 一旦用了就得接受整套表单规范检查，草图会变线框 |

| 变量 | 线框图（第 7 节） | **草图（1.4）** | 为什么 |
| :--- | :--- | :--- | :--- |
| **信息密度** | 真实字段名、真实按钮文案、真实数值 | 3~7 字内容标题 + 灰条表示"这里有一批内容"；只留 1~2 个关键数字做示意 | 写了字段名，用户就会开始讨论字段 |
| **组件精度** | 真组件（`IxTable` / `IxDrawer`）、真实宽度 | 灰块、虚线框，不标像素、不标组件名 | 标了像素，就被当成承诺 |
| **结构规范** | 全项必检 | **只跟 5 条**：主按钮用主题蓝 / 主左取右 / **抽屉页脚贴左、弹窗页脚贴右** / 抽屉·弹窗·整页不混用 / 页面分区骨架一致 | 这 4 条变了，线框就得变形，用户会觉得"方案被改了" |
| **精度规范** | 全项必检 | **一律不管**：精确像素 / 字段名 / 星号占位 / 图标 / 动效 / Token | 跟了这些，草图就被当成成品挑细节 |
| **强调方式** | 靠布局与层级 | 靠**一圈蓝框 + 编号徽标** | 草图只有一件事要强调：**这里是我在发力** |

**允许使用**：页面分区、容器轮廓、占位条 / 占位块、按钮块（**区分主次：主动作用主题蓝实心，次要操作用描边**）、关键数字。
**禁止使用**：真实组件名、像素尺寸、字段名清单、图标、动效、超过三种的颜色。

> 🎨 **颜色只许三种**：灰阶做骨架、`#1C6EFF` 标设计点与主按钮、`#FA8C16` 标风险。**草图上出现第四种颜色，说明有人在表达"好看"，而不是"结构"。**
>
> 🛑 **主按钮必须用主题蓝，这条别省**：草图上主按钮是灰的，用户就分不出"这页的主操作是什么"；到了线框突然变成蓝的，他会问"为什么改了"。**结构级的视觉信号，从草图就要给对。**
>
> ⚠️ **脚本口径说明**：自检脚本第 4 项（色值）与第 10 项（线框规范）**已跳过草图折叠区**，因为草图要到精确像素与完整表单规范这一级才是错的。草图那 4 条结构级规范，**靠第五节自检表人工把关，不掉给脚本**。

### 2. 🛑 框里写"是什么"，不写"为什么"；为什么写进图下说明

> **先分清两种文字，别一刀切**（实测纠正过两次）：

| 文字类型 | 长什么样 | 写在哪 | 原因 |
| :--- | :--- | :---: | :--- |
| **内容信息**（是什么） | 「检测项」「下发范围与影响」「最近一轮检测」 | ✅ **框里** | 全是灰块，别人根本不知道这块是什么内容 |
| **解释信息**（为什么这么设计） | 「系统已按研发机画像出草案」「动手前就知道影响面」 | ❌ 框里 / ✅ **图下标号说明** | 框里写解释挡着看结构；但直接删掉，用户就看不懂——**必须搬到图下** |

**判据一句话**：**框里告诉人"这是什么"；图下告诉人"为什么这么设计"。两边都缺一不可。**

| ❌ 框里别写 | ✅ 框里该写 | ✅ 图下该写 |
| :--- | :--- | :--- |
| 「① 查什么 · 系统已按研发机画像出草案」 | `检测项 · 已按「研发机」预置 12 项` | ① 做法：系统按机器画像先填好……为什么：不用先懂规则、先选范围 |
| 「注：父部门以后新增终端也会被纳入」 | 不写在框里 | ① 为什么：父部门新增终端也要覆盖，否则新机器漏检 |

> 🛑 **每个区块要有一个 3~7 字的内容小标题，但不要带解释**：`检测项`（✅）／`① 查什么 · 系统已按画像出草案`（❌）。
> 🛑 **图上不要写"第几步"式的序号叙事**：标号只用于"图 ↔ 图下说明"对应，不代表操作顺序。

### 3. 标号与区域的画法

| 规则 | 具体要求 |
| :--- | :--- |
| **位置** | 标号一律吸附在区块**右上角**（绝对定位，向外偏 8px），**不许占用正文位置、不许把文字推开** |
| **数量** | **同一组内容只打一个标号**：多个卡片/多行属于同一个设计点时，用**蓝色虚线框整体圈住**，标号打在框的右上角 |
| **形态** | 圆形实心徽标 + 阿拉伯数字（①②③ 与徽标二选一，全篇统一）；不用字母、不用 `Bx` |
| **对应** | 图上有 N 个标号，图下就必须有 N 段说明，编号一致、顺序一致 |
| **设计点区域** | 蓝虚线框圈住；框内正常写内容 |
| **非设计点但必须存在** | 虚线灰框 + 保留内容标题与大致体量（如 `任务列表` + 3 行灰条） |
| **未定的空白** | 留白，不要填"待定" |

> 📌 **相同页不再重复画**：在各自的 tab 里留一个占位条（`P5 规则模板库（抽屉）· 与方案一相同`），保留编号与名称即可。旧规则"共性页照画"已废弃——一半篇幅在重复，用户反而找不到重点。

### 4. 草图自检表（出图前逐条过，全绿才交）

| # | 检查项 | 判据 | 不通过怎么改 |
| :---: | :--- | :--- | :--- |
| 1 | **框里没有解释语，图下有说明** | 框里只有内容标题；解释句全部出现在图下标号说明里；**图上有 N 个标号就有 N 段说明** | 框内解释搬到图下；缺说明的补上 |
| 2 | **每个块有内容标题** | 每块都有 3~7 字说清"这是什么"（`检测项` / `下发结果`）；**不能只剩灰块** | 补标题 |
| 3 | **不出组件名与像素** | 没有 `Ix*`、没有 `px`、没有色值标注 | 全删 |
| 4 | **列名如实、字段值留白** | 需求给的字段名**必须全列**（列名是结构，规划人员靠它核对覆盖）；**单元格里的字段值用灰条占位**（值才是细节） | 补列名；把值换成灰条 |
| 5 | **顶部有页面规模 + 清单** | 第一行是 `需求草图示意` + 那行小字；紧接着"本次需求一共 N 个页面"和页面清单（**5 列：页面/名称/形式/这一页管什么/两套方案**） | 补页头与清单；删掉档位列与 `Bx` |
| 6 | **每个标号都有落点与说明** | 1.3 的每处设计点都能在某页找到一个标号，且图下有对应说明；**图上不出现 `Bx`** | 补标号与说明，或写"本方案不做 + 原因" |
| 7 | **整套覆盖主路径** | 进入 → 操作 → 看到结果，三段都在 | 补页 |
| 8 | **相同页有占位条** | 两套一致的页在各自 tab 里留 `P5 ×××（抽屉）· 与方案一相同`；**没有"见共用页面"的跳转，也没有重复画** | 补占位条 |
| 9 | **10 秒看出差异** | 两个方案的有差异页并排，10 秒内能说出结构差异 | 回第二节①重岔 |
| 10 | **抽屉/弹窗露出背后** | 抽屉类能看到背后承载页的灰化轮廓 | 补背景层 |
| 11 | **只交了 2 套方案** | 没有第三套，也没有常规版 | 删 |
| 12 | **方案名只用两个名字** | 全篇只有「方案一」「方案二」；**没有标题句、没有水位徽标、没有"推荐/次选"** | 删掉标题句与徽标 |
| **13** | **主按钮用主题蓝** | 每页的主操作都用主题蓝实心（`#1C6EFF`），次要操作用描边；**不能全灰** | 给主按钮上色 |
| **14** | **按钮顺序：主在左、取消在右** | 页脚/弹窗底部的双按钮，**主按钮在左、取消/关闭在右** | 调换位置（**此条不能等到线框再改**） |
| **14.1** | **页脚按钮对齐：抽屉靠左、弹窗靠右** | **抽屉页脚按钮组左对齐**（主按钮在最左）；**弹窗页脚按钮组右对齐**。两种容器规则不同，别混用 | 改对齐方式（见下表） |
| **15** | **容器形态不混用** | 抽屉就是右侧抽屉（且露出背后页），弹窗就是居中弹窗，整页就是整页；**三者不互相顶替** | 改回该页真实形态 |
| **16** | **分区骨架定死** | 已画出的分区（顶部区/主内容区/侧栏/操作区）在线框阶段不再增删移动 | 要么现在定，要么现在说不做 |
| **17** | **两维都要有差** | 两套之间**既有走法差异**（页面 / 进入关系 / 主结构），**也有档位差异**；只有档位差 → 判拼盘 | 回第二节①重岔；真岔不开就按 §二④ 特例显式声明 |
| **18** | **创新区留白已交代** | 创新档区域是极简 / 空态，且**图下说明**里写了"系统接管了什么，所以此屏只剩 X" | 补说明；**不许靠把内容填满来装设计感** |
| **19** | **三档没有虚标** | 创新档都能说出"换掉了哪一步分工"；把常规版写成优化版、把优化版写成创新版的，退回重判 | 重判档位，或补做法 |
| **20** | **高水位站得住** | ① ≥2 处 `Bx` 与方案二不同档，且含主战场页；② 说得出"人少干了哪件具体的事"；③ 首屏 / 步数 / 结果三处至少两处不同 | 达不到 → 改叫 `方案一 · 上限版` 并写明天花板；三处全一样 → 只出一套 + 备选档位 |
| **21** | **没有数据就不编数字** | 图上的数字只能来自需求文档或用户给的数据；**没有数据源时写占位 `__ 台` 或标"示意"，不许编造具体值**；写得出数字的，统计方式放图外（方案依据），不写在框里 | 删掉编造的数字，换占位 |
| **22** | **图上只写业务词** | 不出现 `下发 / 收口 / 就位 / 闭环 / 赋能 / 态势 / 影响面 / 走法 / 口径 / 命中 / 待处理 / 依据` 这类词；一律换运营维人员日常说的话（见下方对照表） | 逐词替换 |
| **23** | **冷启动已画** | 新模块 / 新页面必须画 **0 台空态**（含接入途径）；有接入过程的，至少画出"空 / 接入中 / 有内容"中的两态 | 补空态区块或 `P0` 接入页 |
| **24** | **动作覆盖表已交** | PRD 里出现的每个动作 / 状态（安装、升级、卸载、解绑、批量编辑、基础配置、导入、标签、导出…）都在覆盖表里有归属；漏的写"本期不做 + 原因" | 补表；漏项要么补页面，要么显式声明 |
| **25** | **清单与图一一对应** | 页面清单的每一行都能在图上找到对应区块；图上的每个区块也都在清单里，数量一致（一页两态算一页） | 补齐或删掉多余区块 |
| **26** | **tab 与对比表成立** | 顶部有两套方案对比表（整体设计说明 + 思考点，**两套条数可不等**）；两个 tab 内页面顺序与编号一致 | 补对比表 / 重排 tab |
| **27** | **标号位置与数量** | 标号吸附在区块右上角、不占正文位置；**同一组内容用虚线框圈住，只打一个标号** | 调位置 / 合并标号 |
| **28** | **文案过"陌生人复述"测试** | 把任意一句文案单独发给没参与过这个需求的人，他能说出"我要做什么、做完会怎样" | 重写成用户话，删机制名 |

> ⚠️ **14.1 是最容易被做错的一条**，因为两种容器规则确实相反（原始规范见 `comp-drawer.md` 与 `comp-modal.md`）：
>
> | 容器 | 按钮组对齐 | 内部顺序 | CSS |
> | :--- | :--- | :--- | :--- |
> | **抽屉 `IxDrawer`** | **左对齐**（主按钮左间距 16px） | 主按钮在最左，取消在其右 | `justify-content: flex-start` |
> | **弹窗 `IxModal`** | **右对齐** | 主按钮在左，取消在右（组内仍是主左取右） | `justify-content: flex-end` |
>
> 📌 **记法**：**抽屉"靠边站"（贴左），弹窗"按老规矩"（贴右）；两边的内部顺序都是主在左、取消在右。**

> 🔎 **13~16 是"结构级规范"，与 1~12、17~26 不同**：1~12 管的是"草图作为一份沟通材料合不合用"，17~20 管的是"两套方案的差异成不成立、档位有没有真拉开"，21~23 管的是"**图上说的话规划人员信不信、看不看得懂、有没有从 0 讲起**"，24~26 管的是"**PRD 的动作有没有漏、清单与图对不对得上、两套能不能对比**"，13~16 管的是"**草图与线框能不能接上**"。
> 🔎 **为什么这几条不能等到线框再改**：按钮左右反了、抽屉画成弹窗、分区挪了位——这些在用户眼里都是"**我选的方案被改了**"。**结构级的东西，草图就要给对；精度级的，线框再补。**

### 4.1 交付前跑草图门禁（机器把关：结构 5 条 + 文案 7 条）

> 🛑 **1~12 与 17~26 靠人眼，13~16 靠脚本。** 人工自检会漏——**实测就漏过页脚对齐**（抽屉页脚做成了右对齐，肉眼看不出，一跑脚本就报）。

```bash
bash tools/gate-ex.sh 1.4 _output/<业务名>/草图-<业务名>.html
# = EX-1.4-01~07（两套方案 / 对比表 / 相同页占位条 / 图下标号说明 / 禁用内部词 / 页面规模与选定 / 文案表达）+ sketch-selfcheck 5/5
# 退出码 0 = 本环准出，可交给用户选；1 = 修完再交
```

脚本只查这 5 条结构级规范，**不查精度**（像素、字段名、图标、星号占位一律不管）：

| # | 检查项 | 判据 |
| :---: | :--- | :--- |
| 1 | 主按钮用主题蓝 | 有按钮就必须有主按钮，不能全灰 |
| 2 | 按钮顺序 | 不允许「取消/关闭」排在主按钮之前 |
| 3 | 页脚对齐 | 抽屉 `flex-start`、弹窗 `flex-end`；有右对齐页脚时必须也有左对齐页脚 |
| 4 | 容器形态 | 抽屉/弹窗不混用同一页脚 |
| 5 | 不出现规范语义件 | 无 `Ix*` 组件名、无 `wf-form-item` / `wf-form-label` / `req` |

**文案表达机检（EX-1.4-05 / 07，由 `gate.js` 判，不靠自觉）**：

| 子项 | 判据 | 命中后怎么改 |
| :--- | :--- | :--- |
| 内部词与编号 | 不出现 `采信 / 回执 / 留痕 / 处置 / 裁决 / 认领` 与 `B1~B5` | 按 §4.2 对照表换成用户话 |
| 空洞词 | 不出现 `提升体验 / 优化体验 / 更清晰 / 更高效 / 更智能 / 更省心 / 大幅提升 / 赋能 / 极致 / 闭环 / 收口 / 影响面 / 态势` | 换成"能看见什么、能做什么" |
| 每页有说明 | 每个页面块必须有图下标号说明，且必含「为什么」 | 补一段"针对现状里的哪个问题" |
| 做法 / 为什么配对 | 同一页里「做法」与「为什么」条数必须相等 | 一条改法必须配一条理由，缺的补上 |
| 标号一一对应 | 图上标号编号集合 = 图下说明编号集合（**每页单独比**） | 图上有几个标号，图下就写几段；编号必须对齐 |
| 单条长度 | 一段说明不超过 200 字 | 拆成两句，说明还没想清 |
| 按钮文案 | 主按钮不许只写 `确定 / 提交 / 保存 / 是 / 否` | 写明做什么（如"确定并下发"） |

> 📌 **为什么门禁只查这几条，不查全部 28 条**：能机判的只是"硬错"——**词对不对、有没有说明、标号和说明对不对得上**；"这句人话讲得清不清"仍然靠人。**机器管硬错，人管好坏。**

## 六、怎么摆给用户看（呈现形式）

> 三次纠偏都发生过，记住这三条：
> * 第一版：3 个方向 + 对比表 + 顶部台账 → **"太复杂了，全是字，好累"**；
> * 第二版：删得太狠，清单也删了、框里只剩灰块 → **"看不到全貌，也不知道这块是什么内容"**；
> * 第三版：加了"方案标题句 + 3 条差异 + 方案依据 → **"根本看不懂，给其他人讲也讲不了"**。
>
> ✅ **现行结构：清单打底 → 对比表选方向 → tab 内逐页看图读说明。**

```text
① 文件头：标题「需求草图示意」+ 一行小字
② 本次需求一共 N 个页面 + 页面清单（全局，只出现一次）
③ 两套方案对比表：整体设计说明（含代价）+ 各自的设计思考点
④ 切换条（吸顶）：[ 方案一 ]  [ 方案二 ]
   ├ tab 一：P0 → P1 → …（每页 = 草图 + 图下标号说明）；相同页用占位条
   └ tab 二：同上，页面顺序与编号与 tab 一一致
```

> 🛑 **不要"请选择一个方案"这一块**：两个选项各配一段五段代价，用户得读完两段才能比；改成对比表，一眼并排。
> 🛑 **不要方案标题句**：`方案一：系统出草案，人只改差异` 这种压缩句，没读过 1.1~1.3 的人解不出来。**方案是什么，写在「整体设计说明」里。**
> 🛑 **不要"与另一方案的 3 条差异"**：三条差异说不清取舍，也不成体系；差异由对比表逐条对齐。
> 📌 **为什么对比表要放在 tab 之前**：用户先要知道两套各在想什么，再决定往哪套里钻。放在 tab 里，等于逼他先看一套再回来看另一套。

### 0. 页头与措辞规范

| 位置 | 内容 |
| :--- | :--- |
| 大标题 | **`需求草图示意`** |
| 小字说明 | **`基于需求理解之后进行的设计思考草图，仅用于思路对齐，不涉及详细设计。`** |
| 第三行 | **`本次需求一共 N 个页面`** + 页面清单（5 列，见第三节） |

> 🛑 **这行小字不是客套**：它提前把预期钉死——**用户不会拿它当设计稿挑间距和颜色**，也就不会把方向讨论带偏成细节讨论。这句话必须原样出现，不要改写。

**交付话术固定写**：`两套方案的草图都在下面了，你看选哪套；也可以说"选定但要改"，或告诉我哪里不对。`

| 别写 | 该写 | 为什么 |
| :--- | :--- | :--- |
| 继续出**正式线框图** | 继续出**正式**说明书 | 线框图只是说明书里的一节，用户关心的是最终交付物 |
| 继续**进入下一环节** | 继续出正式说明书 | 用户不知道"环节"是什么，他只知道最后要拿到什么 |
| 请选择一个方案（+五段代价） | 两套方案的草图都在下面 | 选择区要读两段长文字才能比；对比表能一眼并排 |

> 🛑 **措辞要对齐用户的预期产物**：用户对接的是"说明书 + 代码"这两样东西；"线框图""页面清单"都是我们的中间件，**不要拿来跟用户对话**。

### 1. 对比表怎么写（本步的核心交付物）

固定两段，**都用表格**：

**第一段：整体对比**（两列并排，一眼读完）

| 对比项 | 方案一 | 方案二 |
| :--- | :--- | :--- |
| 整体设计说明 | `把「<现在怎么做>」变成「<改成怎么做>」。代价：<谁要跟着变、每轮多花/省多少>。` | 同左结构 |
| 一句话区别 | `<两套最根本的分歧，一句话>` | 同左 |
| 本期不做 | `<动作清单>` | 同左 |

> 🛑 **代价必须写进「整体设计说明」的末尾**，不许另起一块、不许灰色小字带过。**没有代价那一行，"高水位"就成了"高级版"**，用户会默认它更好，闭眼选，上线才发现要改流程、改指标。

**第二段：各自的设计思考点**（列：方案 | 编号 | 思考点 | 为什么这么想）

| 方案 | 编号 | 思考点 | 为什么这么想（对应现状里的哪个卡点） |
| :--- | :---: | :--- | :--- |
| 方案一 | 1 | `<用户视角一句话：会看到什么 / 能做什么>` | `<1.1 的卡点原文或用户原话>` |
| 方案二 | 1 | `<……>` | `<……>` |

- **两套条数不要求一致、维度不要求对齐**：硬凑会让话说得别扭；
- **每条必须带「为什么这么想」**，且落在具体卡点上，不写"因为这样更好"；
- **属于取舍的（如"不改分工，所以不派单"）必须写明"取舍"**，不许包装成优点；
- 思考点里**不出现** `Bx`、机制名、形容词（"更清晰""更高效"）。

**命名必须过三关**（思考点、整体说明都要过）：

| 关 | 判据 | 反面（实测犯过） |
| :---: | :--- | :--- |
| **对象** | 有没有**具体的业务对象**（终端 / 客户端 / 任务 / 策略） | `一进来就是没装好的终端`——哪个东西没装好？ |
| **动作** | 有没有**一个能做的动作**，不是"处理""补齐""搞定" | `点一下批量补装`——补装什么？ |
| **条件** | 有没有说清**按什么来选**（清单 / 标签 / 版本差 / 人工勾选） | `系统先判`——判什么、按什么判，全无 |

> 🛑 **禁用词**：`没装好 / 补齐 / 到位 / 闭环 / 收口 / 先判 / 赋能 / 极致 / 最小处理集合 / 采信 / 回执 / 留痕 / 处置 / 裁决 / 认领`。
> 🛑 **自检一句话**：把这句话念给没看过需求的人听，他能复述出"**对这个对象、按这个条件、做这个动作**"，才算过。
> 🛑 **不写"推荐 / 次选"**：一旦标了，用户跳过代价直接选；哪套更合适在交付话术里说一句即可。

### 2. 图下标号说明的固定句式

> **`① 做法：<这处长什么样> 为什么：<针对现状里的哪个问题>`**

- 「为什么」必须指出来源：**来自体验目标，还是来自这类工作的固有毛病**（写成用户的话，不写编号）；
- **代价不用在这里写**：代价在对比表的「整体设计说明」里已经写过一次，图下重复会显得啰嗦；
- 一段一条，**不超过两行**；超过两行说明这条设计点还没想清楚。

### 3. 内部留档要写清"想法从哪来"（不交给用户）

| 行 | 写什么 | 例 |
| :--- | :--- | :--- |
| 突破点落点 | 1.3 的每个 `Bx` 落在哪页哪块 | B1 → P2 顶部来源标签 |
| 档位组合 | 逐个突破点标档，一行读完 | B1 创新版 / B2 创新版 / B3 优化版 / B4 不在本套 |
| 代价五段 | 改动范围 / 影响面 / 上线风险 / 工作量档 / **每轮多花多少人工** | 改 4 页新增 2 页；运维要改习惯；先小范围试 5%；大；每轮多花约 20 分钟 |
| 动作覆盖表 | PRD 的每个动作落在哪页 | 见 §三 |

> 🛑 **不要写"亮点""优势""价值"**：那是营销词。写"为什么这么想"和"代价是什么"，用户自己会判断好不好。

### 4. 图的排布规矩

- **载体是一份单文件 HTML，带 tab 切换**：顶部（页头 / 页面总数 / 清单 / 对比表）固定，下面两个 tab 左右切换；tab 用原生 `radio + label` 或极简 JS 均可，**必须离线可用**；
- 每个 tab 内**按"人怎么走"的顺序排**（进入 → 操作 → 看到结果），**不要在 tab 内把两套的同类页面交叉排**；
- 两套的页面顺序、编号**必须一致**（P0、P1、P2… 同位置），切换时视线不跳；
- 每个页面块固定三段：**页面标题行（`P1 页面名 · 形态 · 这一页管什么`）→ 草图 → 图下标号说明**；说明必须紧跟在它的草图下面，**中间不许插别的内容**；
- 相同页用一行占位条（`P5 规则模板库（抽屉）· 与方案一相同`）带过；
- 每张图配 `P1 / P2` 编号 + `页面名 · 形态`（如「终端详情 · 右侧抽屉」），方便用户指着说"这个第二屏不要"；
- 文件命名：`草图-<业务名>.html`，与说明书的 `design-spec-<业务名>.html` 区分开。

## 七、确认闸门（这一步的重点）

> 🚦 **这是主线上第一个必须停下来等的闸门**，比 5.0 说明书后的确认更早、更关键——**方向错了，后面越细越浪费**。
>
> 🛑 **也是"需求进来之后唯一一次停顿"**：从 1.1 到本步交付，中间**不许停下来提问**（缺什么自己补 `【假设】`，随交付物一起给出）。用户在这一步一次性答复：选哪套、假设对不对、要不要改。**别把问题拆成七八轮问。**

### 停下来时必须做的事

1. **明说我推荐哪个、为什么**（不能把两套方案甩过去让用户自己选，那是把活儿推回去）——**"为什么"必须说那件具体的事**：推荐高水位时，一句话说出"这套让你不用再干 **[X]**"，不许用"更完整 / 更智能 / 体验更好"带过；
2. **明说每套要付的代价**（尤其是我推荐的那套，**五段代价**一句不少，含"每轮多花多少人工"）；
3. **明说哪些地方我还没想清楚**（有就写，没有就说没有）；
4. **选高水位要多付什么，一次说清**：动了哪一步人机分工、要不要新增能力、谁要跟着改习惯——**这几行不许只留成方案依据里的注记**，必须出现在你的这段话里。

### 交付话术的硬上限（用户嫌烦的就是这个）

> 🛑 **确认话术只说"选哪个"，不说"我准备怎么做"。** 用户的判断只需要三样东西：两套差在哪、推荐哪套、要付什么。把执行细节铺在确认语里，等于让他先读一份方案再回答一句"行"。

- **只说四类内容**：① 两套的一句话走法（各一行）；② 我推荐哪套 + 一句"让你不用再干 [X]"；③ 每套代价一句；④ 待确认的 `【假设】`（**≤3 条**，每条一行）。
- **禁止出现在确认话术里**：页面清单与编号、模板 ID、`Ix*` 组件名、Token 与像素值、字段拆分口径、经验编号（`EP-xx` / `D0x-EPxx`）、自检项与状态机、以及"我接下来准备先做 A 再做 B"这类执行排期。这些在草图与说明书正文里，用户要看自己点开看。
- **一句话收尾**：`回"按方案一"或"按方案二"即可；假设不对直接点名第几条。`
- **长度上限**：整段确认话术**不超过 15 行**；超了就是没收敛，回去删。

### 用户可能给的答复，对应怎么走

| 用户答复 | 该怎么处理 |
| :--- | :--- |
| **选一个** | 记录选定结果；**若选的是高水位，同时把"目标与指标变更"一起留档**（见下方铁律），再进 4.1 |
| **选一个但要改** | **先改、再确认、后进线框**——改动如果动到结构（换主结构 / 加减页面），退回本步重出草图，不许直接带去线框 |
| **都不满意** | 不许硬推，也不许直接进线框。问清"是走法不对还是水位不对"：走法不对 → 回第二节①重新想；水位不对 → 回 1.3 补档位点子 |
| **要合并两个方案** | 允许，但必须让用户明确"以哪个为主结构、吸收另一个的哪一处、合并后档位取高的还是低的"，并留档；**防止最后变成四不像** |
| **明确说跳过草图** | 按"方案一直接执行"处理，见下方铁律；跳过只免掉"停下来等"，不免掉草图本身 |

> 🛑 **闸门铁律（默认必停）**：方案未定，不得输出正式页面清单、模板 ID、组件名。**只要用户没有明确说"跳过草图 / 不用草图 / 直接按方案一"，就必须先交草图、停下来等一句选定**——哪怕他这一轮的指令是"给我出设计说明书"、"你直接做吧"，也先出草图再问一句；"要说明书"不等于"授权你替他定方向"。
> 🛑 **明示跳过 = 默认方案一**：仅当用户**明确说出**跳过草图确认（如"跳过草图"、"不用给我看草图"、"别确认了，按方案一直接做"）时，才可越过闸门；此时**默认以草图方案一（高水位）执行**，并在下游交付物开头用一行写明`方案来源：用户明示跳过草图，按方案一执行`。用户只说了跳过、没说哪套的，不再追问，直接取方案一。
> 🛑 **选高水位 = 同时授权改目标**：必须当场把 1.2 的目标句与指标改成方案声明的那版并留档。**否则下游说明书还写着旧目标，新方案拿旧验收线验收，必然打架**——这是高水位方案最容易埋的雷。

## 八、下游怎么接（1.4 → 4.1 的交接契约）

本步交给 4.1 的东西，只有五样，多一样都是负担：

| # | 交接物 | 下游怎么用 | 缺了会怎样 |
| :---: | :--- | :--- | :--- |
| 1 | **选定方案的全套草图** | 4.1 画线框时**按草图的分区与主结构继承**，不许另起炉灶 | 线框和草图对不上，用户会觉得"我选的不是你画的" |
| 2 | **突破点 → 档位 → 页面区域**对照（在本步是"方案依据"里的档位行） | 4.1 逐页核对"这处突破点有没有落点"，并作为经验采纳的靶子 | 突破点做了却没落地，或落地了却没人知道为什么 |
| 3 | **设计说明（含五段代价）** | **只在本步留档，不进说明书**（5.0 已取消「方案取舍 / 档位组合与授权记录」两节）；评审追问时回本步查 | 说明书变长、读者被方案复盘干扰 |
| 4 | **未采纳方案的一句话结论** | 进 5.0，回答"考虑过别的走法吗" | 被质疑"是不是只想到一种" |
| 5 | **档位组合 + 目标/指标变更记录** | 4.1 逐页核"档位有没有降级"；5.0 用**改后的**目标与指标写第一、三节 | 拿旧目标验收新方案，说明书自相矛盾 |

### 继承校验（4.1 必做，回填到本步）

线框画完后必须回头对一次：

| 校验 | 判定 |
| :--- | :--- |
| 主结构是否一致 | 草图是"一屏工作台"，线框不能变成"列表 + 详情两页"——**要变必须先回本步改方向** |
| 页面数量是否一致 | 草图 3 个页面，线框多了 2 个 → 说明草图漏了页面，或线框私自扩张，两者都要回查 |
| 突破点落点是否都在 | 草图里圈的每一处（上限 5 处），线框里必须都找得到；少了就是降级，要有理由 |
| 档位是否被偷偷降级 | 草图定的"创新版/创新版"，线框做成了"优化版" → 判定为执行降级，必须改回或说明原因 |
| 目标是否被悄悄改动 | 方案不得反向修改 1.2 的目标句；若点子确实做到了目标没写到的那一步，**回 1.2 把目标句补到方案实际做到的位置并留痕**（同步，不是授权），不许说明书与目标两套说法 |
| **结构级规范是否继承** | 草图上主按钮在左、用主题蓝、抽屉形态、分区位置——线框必须一致。**这 4 项在草图阶段已定死，线框阶段不许再改** |

> 📌 **一句话概括这张表**：**结构继承，精度重做。** 草图定的分区、页面数、按钮位置与主次、容器形态，线框一律照搬；草图没定的字段、列名、像素、图标、动效，线框全部补齐并按规范检查。
>
> 🛑 **数据也要重做精度（不做就是失败）**：草图上为守"不编数字"而留的 `__`，**线框里一律不许带过去**。线框必须用一套**跨页自洽的示例数据**（对象名 / 数量 / 状态 / 时间 / 证据来源）填满，并补上**草图没展示全的字段与异常态**（长文本截断、空值、无权限、过期、超限降级）；同时在说明书第 7 节开头声明这是示例样本、不构成客户事实。**草图守"结构级"可以空，线框守"落地级"必须满。**

## 九、常见跑偏（反面样本）

| 跑偏写法 | 为什么错 | 改法 |
| :--- | :--- | :--- |
| 给了 3 个方案 + 对比表 + 顶部台账 | **信息过载，用户没耐心看**（第一版实录） | 砍到 2 套，删前置信息与对比表 |
| 把常规版也画出来 | 常规版不需要被选择，只需要被满足 | 删；只在优化版/创新版里体现 |
| 框里带解释句（"查什么 · 系统已按…出草案"） | 干扰信息，挡着看结构 | 搬到图下标号说明里 |
| **框里只剩灰块、没有内容标题** | 别人**不知道这块是什么内容**（第二版实录，矫枉过正） | 补 3~7 字内容标题 |
| **没有页面清单，只按场景切两段** | 用户看不到全貌、不知道本次一共几个页面 | 开头补清单 + 相同页做共用区 |
| **共性页只在其中一套里画** | 另一套链路断裂，用户切过去找不到这一屏 | 两套都画，右上角标灰底 `两方案相同`（**重复画是对的，别省**） |
| 两个方案只是侧栏位置不同 | 结构没岔，是同一个方案的变体 | 回第二节①，从"谁先动 / 任务放在哪"重岔 |
| 草图里画了完整的表格列、写了字段名 | 精度跑到线框去了，用户会在细节上挑 | 退成灰条 |
| 只画了首页 | 走法站不站得住要连起来看 | 补成整套（进入 → 操作 → 结果） |
| 设计说明只写好话，不写代价 | 没取舍等于没判断 | 按"代价是…"强制补全 |
| **两套走法一样、只是档位不同（拼盘）** | 用户选的还是同一件事，只是精细度；创新没变成可选项 | 回第二节①重岔走法；真岔不开，按 §二④ 特例显式声明并补"创新档会变成什么样" |
| **两套水位一样高** | 高水位点子进不了方案主体，只能降档成一行注记 | 按 §二② 配档：方案一 ≥2 处创新，方案二全部优化版 |
| **方案一写满创新档，却不写目标与指标怎么变** | 把"改前提"藏进漂亮方案里，上线才发现要改流程、改验收线 | 创新档必带"目标改哪句 / 指标换哪个 / 怎么防误伤"三行 |
| 用户说"都不满意"，我加第三个硬凑 | 没搞清是走法问题还是水位问题 | 先问一句，再决定回岔还是回 1.3 补档位 |

## 十一、与其余环节的边界

| 易混环节 | 分工 |
| :--- | :--- |
| **1.3 突破点拆解** | 1.3 出"打法点子"，本步出"页面形态"。**1.3 的档位表是原料，本步的草图是组装结果**——同一个突破点在两个方案里可以取不同档 |
| **本步的页面草图清单 vs 4.1 的正式页面清单** | 本步定"几屏、各管什么、两个方案哪里不一样"（粗）；4.1 定"编号、模板 ID、组件、Token"（细）。**见第三节** |
| **4.1 线框图** | 本步只定"分区与主结构"，4.1 定"分区里放什么组件、多少列、多宽"。**精度差别见第一节** |
| **5.0 说明书** | 选定方案的设计说明与未采纳方案的一句话结论，进说明书；草图本体**不进说明书**（避免和线框图混） |

> 📌 **一句话记法**：**1.3 说怎么破，1.4 说长什么样、走哪套，4.1 说具体怎么摆，5.0 说清为什么这么摆。**
