# ③ 排障闭环

> 💡 **用途**：作为 [1.3 体验突破点拆解](../1.3-体验突破点拆解.md) 第八节「入口 2：按用户工作类型扫」的经验底座。
>
> 🧠 **这是一份"怎么想"的经验，不是"怎么做"的答案库。**
> 用法顺序固定：**先按原则定症结 → 再想办法变出别的做法 → 最后拿参考解法对照补充**。参考解法只用于打开思路和查漏，不是匹配源。
>
> 📌 **边界**：这是**方案设计阶段的思考经验**，只管"往哪个方向想、变成什么形态"，不管"用什么手段实现"。落地技法走 Type-01~07 等执行侧经验。
>
> 🚧 **状态**：初稿，未验证。四类初稿已齐。

## 一、这类工作在干什么

处置告警和报障、排查异常、复核归档——本质是三步：

> **先定位（问题在哪）→ 再分析原因（为什么会这样）→ 最后闭环（处置、流转、确认恢复）**

定位不准，后面全白搭；证据说不清，人不敢下结论；闭环不畅，问题一直拖着。

和 ② 运营分析的分工：② 判"有没有事、要不要管"，③ 接着判"事在哪、为什么、怎么收"。

扫之前先自问一句（问的是**当前这个场景 / 页面**，不是整个需求）：

> 这块界面上，用户卡在哪一步——定位、看证据，还是收尾？

- 定位错 → 修错地方，二次故障。
- 证据说不清 → 判断错，处置方向就偏。
- 闭环拖 → 故障时间被拉长，一线和用户都在等。

---

## 二、拔高方向（一句话）

> 别只让用户"一步步试"，要让他"**快找到位置、看得懂为什么、几步就能收尾**"。

---

## 三、原则（判据）

扫需求时，逐条问右边的扫描问句。**发现"有问题"还不够，要定到具体是哪一种病**。

| # | 原则 | 什么意思 | 常见症结 | 扫描问句 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | **快速定位到点上** | 从"打不开""很慢"这种笼统现象，尽快收敛到一个具体的对象、环节或组件；不用挨个试、不用全链路猜 | ① 只有整体现象，没有可查的线索，不知道往哪看<br>② 关键信息被埋在长列表、深页面里，要翻找<br>③ 对象太多，只能靠记忆或逐条筛<br>④ 信息散在几处，拼不出全貌 | 他多快能指到具体的地方？ |
| 2 | **证据看得懂** | 判断原因用到的信息摆在一起、看得懂、对得上——现象、证据、结论能连起来，不用自己翻译 | ① 只给结论，不给依据<br>② 证据是原始数据，要自己解读<br>③ 证据和结论对不上，或散在几个系统 | 他能不能一眼看懂"为什么是这个原因"？ |
| 3 | **闭环动作高效便捷** | 从确定原因到事情结束，动作少、路径顺——处置、跨团队流转、确认恢复在一处走完 | ① 处置要跳几个系统<br>② 流转靠群里喊，状态不可见<br>③ 改完还要打电话确认 | 从"知道原因"到"这件事结束"，要点几下、找几个人？ |
| 4 | **同类的别再从头查** | 这次的定位和原因能留下来，下次同类问题能直接用 | ① 归档只写"已处理"<br>② 同类问题下次还从零查<br>③ 根因没归类，统计不出来 | 下个月再出同样的问题，能少走多少步？ |

> 🛑 **别四条全上**：做故障定位的场景，第 1、2 条是主角；做工单流转的场景，主角是第 3、4 条。

> ⚠️ **例外**：如果这个页面同时承担"定位 + 处置 + 归档"（常见于中小团队的合一工作台），四条会全中。这时按"哪一步现在最耗时"定主角，其余三条仍要进基线，不能因为不是主角就不做。

> 🔍 **"找不到"分四种，解法不一样**：不知道往哪看 → 给线索；信息被埋着 → 突出展示；对象太多 → 要能筛能搜；东西散在几处 → 要聚到一处。别笼统记一句"不好找"，否则变出来的做法会不对路。

> 📐 **1 和 2 的分界**：1 管"把问题指到一个位置"，2 管"确认这个位置就是原因"。同样是"东西散"，找位置时记 1，确认原因时记 2。

### 基线下限（缺了直接补，不用发散）

| 对应原则 | 基线该有什么 |
| :--- | :--- |
| 快速定位到点上 | 看得到相关对象和环节的状态，能排序、能筛、能搜 |
| 证据看得懂 | 能看到现象、相关指标和日志 |
| 闭环动作高效便捷 | 能处置、能流转、能标记解决 |
| 同类的别再从头查 | 归档能写现象和原因 |

## 四、怎么往上想：换个做法

定了症结之后，**先别去看第六节的参考解法**。问一句：**这件事还能从哪儿变？**

> 🔗 **和 1.3 变维表的关系**：这六处是把 1.3 的通用六维换成本域说法，另加两处本域专用的——**证据怎么摆**和**闭环到哪算完**。

| 能变的地方 | 可以变成 | 变完大概到哪档 |
| :--- | :--- | :---: |
| 从哪开始 | 从现象 / 从影响面 / 从最近变更 / 从一次具体请求或操作 | 优化~创新 |
| 定位的粒度 | 整体 / 一类对象 / 一个对象 / 一次具体请求或操作 | 优化 |
| 怎么找出来 | 人逐条翻 / 排序、筛选、搜索 / 系统按可疑度推 / 系统直接给结论、人验证 | 优化~变革 |
| 证据怎么摆 | 散在几个系统 / 同屏并排 / 按因果串成链 / 只给结论和判定依据 | 优化~创新 |
| 动手的方式 | 人手工 / 按脚本 / 系统执行人确认 | 优化~变革 |
| 闭环到哪算完 | 提交处置 / 状态流转完 / 用户确认恢复 / 观察一段不复发 | 优化~变革 |

两条用法：

1. **至少动两个地方，才算一条新做法。** 只把同一张表换个位置摆，不算。
2. **变完校验一句**：这条做法替用户省了哪份力——找、读、判断、重复、返工。说不出来，退回重想。

> 前三个地方管"定位"，第四个管"证据"，后两个管"闭环"——正好对上这类工作的三步。

## 五、走一遍示例（示意走法，不是答案）

拿原则 2 的症结②"证据是原始数据，要自己解读"走一遍。**不用六处都动，动两处就够一条**：

| 变的地方 | 变出来的做法 | 怎么解决"要自己解读" | 档位 |
| :--- | :--- | :--- | :---: |
| 证据怎么摆 → 同屏并排 | 现象、指标、日志、最近变更放在一屏 | 先解决"散"，不用来回切 | 优化 |
| 证据怎么摆 → 只给结论和判定依据 | 一句结论 + 两三条关键证据，其余折叠 | 不用读原始数据 | 创新 |
| 证据怎么摆 → 按因果串成链 | 事实按发生顺序串起来，标出哪条是判定依据 | 从"一堆数据"变成"一条线" | 创新 |
| 怎么找出来 → 系统直接给结论 | 系统给"卡在哪、为什么"，人核对 | 从看数据变成核对结论 | 创新~变革 |
| 闭环到哪算完 → 用户确认恢复 | 证据里直接带恢复确认 | 判断和收尾连在一起 | 优化~创新 |

> 🛑 这些不是答案，是走法示范。换个症结要重新变，**不要回来抄**。

**再换一个非链路的例子**：账号类问题——某人说"密码没错，就是登不进去"。

| 变的地方 | 变出来的做法 | 档位 |
| :--- | :--- | :---: |
| 从哪开始 → 一个具体账号 | 直接看这个账号的锁定状态、最近失败记录、权限变更 | 优化 |
| 怎么找出来 → 系统直接给结论 | 登录失败页直接给判断："连续 5 次密码错误被锁 / 密码过期 / 权限被回收" | 创新 |
| 证据怎么摆 → 只给结论和判定依据 | 一句结论 + 两条依据（锁定时间、失败次数），人核实 | 创新 |
| 闭环到哪算完 → 用户确认恢复 | 解锁后让本人用一次登录确认，而不是看他"应该好了" | 优化~创新 |

## 六、参考解法（只做参考，不是匹配源）

> ⚠️ **使用顺序**：先按第四节自己想一轮，再回来对照，用来打开思路、查漏。
> 这里不是匹配表；真用了，要能说出"这个需求为什么是它"。
>
> 📊 **表内按档位从低到高排**：前半段是行业通用做法（置顶、筛选、搜索、就地展开这类），只从这儿挑，做出来一定"不落后但不出彩"；**至少要往创新档想一条**，差距都在后半段。
> ⚖️ **档位是按"用户还要出多少力"判的**，表里的标签只是参考，同一个做法换个需求可能差一档，别照抄。

### 对应 1 · 快速定位到点上

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 关键信息置顶、标出来，默认按可疑度排 | 优化 | 找 | 信息被埋在列表深处时 |
| 按对象、时间、维度筛，筛完接着往下查不丢条件 | 优化 | 找 | 对象数量大时 |
| 支持按 IP、账号、域名这些手上的线索直接搜 | 优化 | 找 | 用户已经知道找什么时 |
| 把现象拆成可排查的几类（链路、配置、账号、终端），每类给判断依据 | 优化 | 判断 | 原因类型多时 |
| 从具体个体出发（一个用户、一次操作），而不是看聚合指标 | 创新 | 判断 | 聚合把个体问题抹平时 |
| 把"问题开始时间"和"最近的变更"自动对齐，直接给嫌疑变更 | 创新 | 判断 | 环境变更频繁时 |
| 多个报障自动找共同点（同一节点、同一策略、同一时段），直接给共因 | 创新 | 判断 | 同时来一批报障时最值 |
| 按现象搜，不按字段搜（"最近两天打不开的终端"） | 创新 | 找 | 线索只是模糊描述时 |
| 一句话定位：用自然语言说现象，系统直接给位置和原因 | 创新~变革 | 判断 | 用户说不清技术细节时 |
| 系统自动跑一轮排查，把大部分可能排除掉，只把剩下的交给人 | 创新~变革 | 判断 | 排查步骤固定、可枚举时 |
| 用户还没报，系统已经定位到异常并推过来 | 变革 | 找 | 有持续观测能力时 |

### 对应 2 · 证据看得懂

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 现象、指标、日志、最近变更同屏并排 | 优化 | 找 | 证据通常散在几个系统 |
| 关键字段高亮，别让人逐行找 | 优化 | 读 | 日志类证据 |
| 只给结论 + 两三条关键证据，其余折叠 | 创新 | 读 | 证据多、用户非专家时 |
| 每条证据标注它支持还是排除哪个原因 | 创新 | 判断 | 原因有好几种可能时 |
| 同时给反证：为什么不是 DNS、不是证书、不是策略 | 创新 | 判断 | 结论容易被质疑时 |
| 多个系统的日志按同一时间轴对齐，时钟偏差也校正 | 创新 | 判断 | 跨系统取证时 |
| 把一次会话或一次请求回放出来，证据自己会说话 | 创新 | 判断 | 有请求级数据时 |
| 系统直接解释"为什么是这个原因"，并按受众换详略 | 创新~变革 | 判断 | 结论要拿给客户或主管看时 |

### 对应 3 · 闭环动作高效便捷

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 就地处置，不跳系统 | 优化 | 找 | 全类通用 |
| 处置、流转、确认在一处完成，状态一直可见 | 优化~创新 | 重复 | 跨团队处理时 |
| 交接时带上已排查结论和下一步，不用重新描述 | 创新 | 重复 | 多团队接力时最值 |
| 按定位结果直接推荐处置方案，并说明会影响到谁 | 创新 | 判断 | 处置方式有多种选择时 |
| 一个事件一个协作空间，各方在同一条时间线上 | 创新 | 重复 | 多方同时处理时最值 |
| 超时自动升级，不用人催 | 创新 | 重复 | 值班制度成熟时 |
| 处置前先模拟影响，再决定做不做 | 创新~变革 | 判断 | 动作本身有风险时 |
| 处置后自动验证、自动关单，不用人回访 | 变革 | 返工 | 验证指标明确时 |
| 常见故障自动处置，人只确认 | 变革 | 判断 | 结论稳定、后果可控时 |

### 对应 4 · 同类的别再从头查

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 归档结构化：现象、根因、处置、影响面 | 优化 | 找 | 全类通用 |
| 新报障自动匹配历史相似案例，直接给上次的结论 | 创新 | 判断 | 历史积累足够多时 |
| 把某类问题的排查步骤沉淀成可执行的检查清单，下次照着跑 | 创新 | 重复 | 排查步骤固定时 |
| 根因聚类，按类统计，看得出哪类问题最费人 | 创新 | 判断 | 问题量大时 |
| 关闭时自动生成复盘草稿，人只补两句 | 创新~变革 | 重复 | 有复盘要求时 |
| 处置动作固化成自愈规则，同类问题自己处理 | 变革 | 重复 | 同类占比高、处置稳定时 |

### 全类通用 · 具象化（把抽象变成看得见的）

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 排障 = 排除法：可能的原因一条条划掉，剩下那个就是 | 优化~创新 | 判断 | 原因类型多、可枚举时 |
| 证据 = 一页病例：症状、检查结果、判断、处置写在一页 | 创新 | 读 | 证据多、要给别人看时 |
| 排障 = 沿路找断点：一条路上逐段亮灯，哪段黑就是哪段 | 优化~创新 | 判断 | 链路类问题 |
| 一次访问 = 一份行程记录：每一跳到哪、花了多久 | 创新 | 判断 | 有请求级数据时 |
| 闭环 = 一张交接单：谁接、做到哪步、下一步是什么 | 优化 | 重复 | 多团队接力时 |

> 🛑 **具象化不是画得花哨**：形态要跟用户脑子里那件事的过程对得上；对不上，就只是装饰。

## 七、怎么用（三步）

> 📐 **扫描粒度：场景 / 页面 / 任务，不是"需求"**。
> 一个报障流程里可能有接单页、定位页、处置页、归档页，**逐个场景判断**，一个需求可以同时命中多类经验。

> 🧩 **原则不是每个页面的验收单**：这块工作正好按三步走，每条原则对应其中一步。

| 阶段 | 主要原则 |
| :--- | :--- |
| 定位 | 快速定位到点上 |
| 分析原因 | 证据看得懂 |
| 闭环 | 闭环动作高效便捷 |
| 复盘 / 归档 | 同类的别再从头查 |

> 反查用：这三步里哪一步没有页面承接，闭环就在那里断了——最常见的断点是「看证据」（定位完了还要自己拼证据）和「收尾确认」。

1. **先拿现状做底**：先看 1.1 里这个场景现在多慢、卡在哪，扫句才有东西可答。再问这块界面主要卡在定位、看证据，还是收尾——卡定位 → 第 1 条；卡看证据 → 第 2 条；卡收尾 → 第 3 条。
2. **逐条扫，定症结**：用扫描问句一条条问，记到具体症结（①②③），别只写"排障效率低"。
3. **变出做法，再对照**：拿症结对照第四节的六处地方，变出几条结构不同的做法；想完再看第六节，缺的补、重的删。还原成一句"让人……"，和入口 1 的结果**合并去重**，回到 1.3 第 3 步分档。

> ⚠️ 只走入口 1 的时候，第 2、4 条几乎不会被触发——目标里很少写"证据要看得懂""下次别再查"，但这两段恰恰最耗人。

## 八、扫描示例：跨域排障提效

> 示例只演示扫法，场景细节以实际需求为准。

| 原则 | 扫到的答案 | 症结 | 目标里有没有提 | 转成的突破点 |
| :--- | :--- | :---: | :---: | :--- |
| **快速定位到点上** | 只能一段段 ping、traceroute，手工拼结论 | ①② | **提了（10 分钟定位）** | 让异常位置自己显形 |
| 证据看得懂 | 证据在四个系统里，结论靠老员工凭经验拼 | ②③ | 没提 | 让人一屏看懂"为什么卡在这" |
| 闭环动作高效便捷 | 四个团队群里同步，改完还要打电话确认 | ①②③ | 提了（跨域） | 让流转和确认在一条线上走完 |
| 同类的别再从头查 | 归档只写"已处理"，同类问题下次从头来 | ①② | 没提 | 让这次的结论变成下次的起点 |

结论：目标只覆盖了「定位」和一部分「跨域」；「看证据」「收尾确认」「沉淀」都是入口 2 补的。
