## 一、这类工作在干什么

研判告警、查日志、做分析、挖威胁——这四件事不是四类工作，是**一条链上的四段**：发现信号 → 查证真假 → 分析影响 → 往深处挖。

共同点是：**用户在从一堆信号里，下一个能拿去行动的判断**。

扫之前先自问一句（问的是**当前这个场景 / 页面**，不是整个需求）：

> 这块界面上，用户要下的是什么判断？判错了会怎样？

- 漏判 → 真威胁被放过去，代价在安全侧。
- 误判 → 白花人力，甚至误处置打断业务。

两头都有代价，所以「给结论快」不能拿「依据看不见」去换。

---

## 二、拔高方向（一句话）

> 别只让用户"看完数据自己判断"，要让他"**打开就知道有没有事、凭什么这么判、下一步该干什么**"。

这类工作最贵的成本不是操作时间，是**注意力**——一天看几千条，人的判断力会被磨钝。

## 三、原则（判据）

扫需求时，逐条问右边的扫描问句。**发现"有问题"还不够，要定到具体是哪一种病**。

| # | 原则 | 什么意思 | 常见症结 | 扫描问句 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | **打开就见结论** | 一进来就知道有没有事、是什么事、要不要管。**管"有没有结论、结论能不能拿去行动"**，不管它写得好不好读 | ① 首页全是指标和图，没有结论<br>② 有结论但太笼统，不能拿去行动<br>③ 重要的事混在次要的事里<br>④ 看不出结论有多确定，不知道该不该人工复核 | 他打开这一屏，是先看到结论，还是先看到一堆数据？ |
| 2 | **结论查得到依据** | 结论旁边就有证据，不用切工具、不用凭经验补 | ① 结论是黑盒，只给个风险分<br>② 证据散在多个系统里<br>③ 给的是原始日志，还得自己解读 | 他不信这个结论时，能在原地找到依据吗？ |
| 3 | **该看的浮上来** | 重复的合并、低价值的压下去，把需要人判断的留给人 | ① 同一条告警反复报<br>② 低危淹没高危<br>③ 不知道哪些被系统自动忽略了 | 这一屏里，有多少是重复的、本来可以自动合并的？ |
| 4 | **判断能一路走到底** | 从看到、查证到下结论，上下文不丢，不用换工具重来 | ① 换页丢掉筛选和时间窗<br>② 查到一半要跳去别的系统<br>③ 结论没地方落，靠截图和嘴说 | 他从"看到"走到"下结论"，中间要换几次工具、丢几次上下文？ |
| 5 | **判过的能留下** | 这次怎么判的能查，同类下次能复用 | ① 每次从零研判<br>② 经验只在个别人脑子里<br>③ 处置完不回写，下次还这么判 | 这个问题上个月判过吗？当时怎么判的还查得到吗？ |
| 6 | **结论和证据读得进去** | **管表达质量**：关键信息一眼能捞到，不用通读；证据清楚，能看出哪一条是判定的关键 | ① 结论是一大段话，读到结尾才知道说啥<br>② 证据是整段原始日志，关键行得自己找<br>③ 多条证据并排摆着，看不出先后和因果 | 他看结论和证据时，是在"扫"，还是在"读"？ |

> 📐 **1 和 6 的分界**：1 问"有没有结论、结论能不能拿去行动"，6 问"结论和证据写得好不好读"。同一条现象只归一处——"太长，得通读"归 6；"太笼统，没法行动"归 1。

> 🛑 **别六条全上**：原则是扫描方向，不是验收项。做告警降噪的需求，「该看的浮上来」是主角；做威胁狩猎的需求，主角多半是「查得到依据」和「结论和证据读得进去」。

> ⚠️ **例外**：同一个页面里如果用户的任务是"判完就要定结论并交出去"（如多场景研判台的统一研判单），六条可能同时成立。这时不必砍，按"结论错了代价有多大"排优先级——「查得到依据」「该看的浮上来」优先，其余作基线补齐。

### 基线下限（缺了直接补，不用发散）

| 对应原则 | 基线该有什么 |
| :--- | :--- |
| 打开就见结论 | 列表能看状态、优先级，能筛 |
| 结论查得到依据 | 详情里看得到命中规则和原始日志 |
| 该看的浮上来 | 告警能按规则/实体聚合，能标记误报 |
| 判断能一路走到底 | 列表能进详情，处置能留记录 |
| 判过的能留下 | 研判记录能查 |
| 结论和证据读得进去 | 结论一句话能看懂，日志能定位到关键行 |

## 四、怎么往上想：换个做法

定了症结之后，**先别去看第六节的参考解法**。问一句：**这件事还能从哪儿变？**

下面六个地方都能变。变哪一处，做法就跟着换一种。

> 🔗 **和 1.3 变维表的关系**：**这不是 1.3 通用六维的翻译，是本域自己的一张变维表。** 和通用六维（信息在哪层 / 走几步 / 上下文丢不丢 / 谁先动 / 什么时候给 / 默认状态）只是部分重叠——"谁来筛"对"谁先动"，"在哪判断"对"信息在哪层 / 走几步"；**"判断的粒度"和"结论怎么落"是本域独有的**。**直接用这张，不用回套通用六维**；这张发散不够，再拿通用六维补。

| 能变的地方 | 可以变成 | 变完大概到哪档 |
| :--- | :--- | :---: |
| 先给什么 | 原始数据 / 指标图 / 一句话结论 / 结论带依据 | 基线~优化 |
| 谁来筛 | 人逐条看 / 系统聚合去重 / 系统先给判断、人只确认或推翻 | 优化~创新 |
| 判断的粒度 | 单条告警 / 一个事件 / 一个实体（资产、账号、域名） / 一类行为 | 优化~创新 |
| 时间视角 | 当前快照 / 一段时间的变化 / 与历史同期比 | 优化~创新 |
| 在哪判断 | 列表里 / 详情页 / 图上 / 对话里 | 优化~创新 |
| 结论怎么落 | 就地标记 / 转工单 / 写成规则 / 什么都不落 | 优化~创新 |

两条用法：

1. **至少动两个地方，才算一条新做法。** 只改图表样式、只把列表换成卡片，不算。
2. **变完校验一句**：这条做法替用户省了哪份力——找、读、判断、重复、返工。说不出来，退回重想。

> 「判断的粒度」是这类工作最容易出彩的一处：单条告警永远判不完，但**一个实体**可以被持续观察，**一类行为**可以被总结成模式。粒度一换，工作量会掉一个量级。

## 五、走一遍示例（示意走法，不是答案）

拿「结论查得到依据」的症结②"证据散在多个系统里"走一遍：

| 变的地方 | 变出来的做法 | 怎么解决"散" | 档位 |
| :--- | :--- | :--- | :---: |
| 先给什么 → 结论带依据 | 结论旁直接挂三类证据：命中规则、日志片段、实体画像 | 证据跟着结论走，不用自己去找 | 优化 |
| 在哪判断 → 同屏 | 三类证据在详情页分区摆放，不跳系统 | 还是在一个页面里看 | 优化 |
| 判断的粒度 → 事件 | 同一实体的多条告警合成一个事件，证据自动归到同一个案卷 | 来源再多，也归到一个案卷 | 优化 |
| 时间视角 → 一段时间 | 跨系统的事实按发生顺序并到一条时间线上 | 散在各处的事实变成一条链 | 创新 |
| 谁来筛 → 系统先判断 | 系统先把跨系统证据对齐，给建议结论，人只核对 | 对齐由系统做，人不用拼 | 创新 |
| 在哪判断 → 对话里 | 直接问"为什么判高危"，系统把散在各处的证据一次答全 | 一个入口问全，不用逐个系统翻 | 创新~变革 |

> 🛑 这六条不是答案，是走法示范。换个需求，要重新拿症结从六处地方变，**不要回来抄**。

## 六、参考解法（只做参考，不是匹配源）

> ⚠️ **使用顺序**：先按第四节自己想一轮，再回来对照，用来打开思路、查漏。
> 这里不是匹配表；真用了，要能说出"这个需求为什么是它"。
> 📊 **表内按档位从低到高排**：只从优化档挑，做出来一定"不落后但不出彩"，至少往创新档想一条。
> 🧮 **档位后面那句"还得出力"就是这档的依据**：创新档及以上的条目都跟了一句"用户还得自己出什么力"。**这句话写不出来，说明这条实际只到优化档，别往上报**；往 1.4 报水位时，直接用它答"人少干了哪件事、还剩哪件事"。

### 对应 1 · 打开就见结论

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 顶部结论条：今天有几件事需要你判断，按轻重排好 | 优化 | 找 | 事件量大的场景 |
| 列表顶部概览卡：待研判多少、高危多少、和昨天比怎么样，先给全貌 | 优化 | 找 | 告警列表页，量大时最有用 |
| 事件卡片三段式：发生了什么、影响谁、建议怎么做 | 优化 | 判断 | 单条告警信息不全时 |
| 默认视图只给"待研判"，已闭环的折叠 | 创新｜还得出力：判断已闭环的要不要回看 | 找 | 有明确闭环流程的产品 |
| 结论带置信度：高置信直接给处置建议，中置信标"建议复核"，低置信只做提示 | 创新｜还得出力：中低置信仍要自己判 | 判断 | 误判代价高的场景 |
| 高置信事件自动闭环，人只抽检；抽检发现问题再回退 | 变革｜还得出力：抽检发现问题要退得回去 | 判断 | 误报率已经压得很低时 |

### 对应 2 · 结论查得到依据

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 结论旁挂证据：命中规则、原始日志片段、相关实体 | 优化 | 读 | 全类通用 |
| 证据串成时间线，按发生顺序讲一遍 | 创新｜还得出力：自己把时间线读成因果 | 判断 | 有多步行为的攻击 |
| 也能看"为什么没报"：把反证摆出来 | 创新｜还得出力：判断反证够不够 | 判断 | 用户常质疑漏报的场景 |

### 对应 3 · 该看的浮上来

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 同一实体、同一规则、时间窗内合并成一条事件 | 优化 | 重复 | 告警量大时最值 |
| 按影响面和置信度分级，低价值的自动折叠 | 优化 | 判断 | 有分级依据才可信，乱分级反而更乱 |
| 把"被自动忽略的"也摆出来，可查可申诉 | 创新｜还得出力：偶尔翻一下漏没漏 | 判断 | 降噪做得越狠，这条越必要 |

### 对应 4 · 判断能一路走到底

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 就地从列表展开到日志、到处置，不跳页 | 优化 | 找 | 全类通用 |
| 筛选条件、时间窗跟人走，换页不丢 | 优化 | 重复 | 多页联查的场景 |
| 结论就地落：标记、转工单、加备注 | 优化 | 返工 | 有处置流程的产品 |

### 对应 5 · 判过的能留下

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 研判记录可查可搜：谁、依据什么、判成什么 | 优化 | 找 | 多人轮班的团队 |
| 相似事件推荐：这类告警上次怎么判的 | 创新｜还得出力：判断这次和上次是不是同一回事 | 判断 | 历史积累足够多时 |
| 结论回写规则：确认误报的，一键变成抑制条件 | 创新~变革｜还得出力：确认抑制不会把真攻击一起压掉 | 返工 | 误报反复出现的场景 |
| 研判经验自动固化成检测 / 抑制规则，系统自己迭代，人只审规则 | 变革｜还得出力：审规则、担规则的责任 | 重复 | 研判量大、结论稳定的场景 |

### 对应 6 · 结论和证据读得进去

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 结论前置成一句，后面跟三个点：谁、做了什么、影响什么 | 优化 | 读 | 全类通用 |
| 原始日志里把关键字段高亮，别让人逐行找 | 优化 | 读 | 日志类证据 |
| 证据按时间或因果排成链，标出哪一环是判定依据 | 创新｜还得出力：自己确认哪一环说了算 | 判断 | 多步行为、多条证据时 |
| 长文本先给摘要，点开再看全文 | 优化 | 读 | 报告、情报类内容 |
| 关键数字给对比基线（失败率 92%，平时 2%） | 优化 | 判断 | 单看数字没感觉的场景 |

### 全类通用 · 具象化（把抽象变成看得见的）

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 研判 = 法庭：结论、证据、反证三样摆齐 | 创新｜还得出力：把三样摆全并下判断 | 判断 | 结论容易引起争议的场景 |
| 一次攻击 = 一条故事线：从哪进来、做了什么、影响了谁 | 创新｜还得出力：自己把步骤连起来核一遍 | 判断 | 多步攻击、跨实体关联时 |
| 一堆告警 = 分诊台：先分轻重，再送不同的人 | 优化~创新｜还得出力：定分级标准 | 找 | 告警量大、多人分工的团队 |
| 分析 = 关系图：人、资产、行为之间的连线 | 创新｜还得出力：自己从连线里读关系 | 判断 | 关系比数值更重要时 |
| 研判结论 = 一页摘要 + 附卷：主结论一页看完，证据作为附件逐层展开 | 创新｜还得出力：判断摘要够不够用 | 读 | 结论和证据都很长时 |

> 🛑 **具象化不是画得花哨**：形态要跟用户脑子里那件事的过程对得上；对不上，就只是装饰。

## 七、怎么用（三步）

> 📐 **扫描粒度：场景 / 页面 / 任务，不是"需求"**。
> 一个需求里可能有告警列表、事件详情、日志查询、威胁狩猎几个页面，**逐个场景判断**，一个需求可以同时命中多类经验。

> 🧩 **原则不是每个页面的验收单**：一个页面通常只承接其中两三条，剩下交给链路上的其他页面。判断依据不是"这是什么页面"，而是"它在链路上承担哪一段"。

| 链路段 | 主要原则 |
| :--- | :--- |
| 发现 / 浏览（如告警列表） | 打开就见结论 + 该看的浮上来 |
| 查证 / 研判（如告警详情） | 结论查得到依据 + 结论和证据读得进去 + 判断能一路走到底 |
| 沉淀 / 复盘（如研判记录） | 判过的能留下 |

> 反查用：哪条原则在所有页面上都没人承接，说明流程缺了一段，不是页面没做好。

1. **先问代价**：这块界面上下的是什么判断，判错了是漏还是误？漏判为主 → 第 2、3 条是主角；误判为主 → 第 1、4 条更关键。
2. **逐条扫，定症结**：用扫描问句一条条问，记到具体症结（①②③），别只写"信息太多"。
3. **变出做法，再对照**：拿症结对照第四节的六处地方，变出几条结构不同的做法；想完再看第六节，缺的补、重的删。还原成一句"让人……"，和入口 1 的结果**合并去重**，回到 1.3 第 3 步分档。

> ⚠️ 只走入口 1 的时候，第 1 条（打开就见结论）几乎必然被漏——目标里很少会写"先给结论"，但那恰恰是这类工作最大的痛点。

## 八、扫描示例：告警降噪与研判提效

> 示例只演示扫法，场景细节以实际需求为准。

| 原则 | 扫到的答案 | 症结 | 目标里有没有提 | 转成的突破点 |
| :--- | :--- | :---: | :---: | :--- |
| 打开就见结论 | 首页给的是一堆趋势图，人自己找哪里不对 | ① | 没提 | 让人一进来就看到今天要判的几件事 |
| 结论查得到依据 | 详情只有一句"命中规则 X"，日志要跳去另一个系统查 | ①② | 提了（研判提效） | 让人在原地看到凭什么这么判 |
| **该看的浮上来** | 同一条告警一天报几百次 | ①② | **提了（降噪）** | 让重复的自动合并，只看一次 |
| 判断能一路走到底 | 判完切到工单系统再写一遍 | ②③ | 没提 | 让人判完就地落结论，不用二次搬 |
| 判过的能留下 | 误报下次还报，没人回写 | ①③ | 没提 | 让判过的结论能变成下次的依据 |
| 结论和证据读得进去 | 研判页是一大段系统结论 + 全量日志，关键几行靠人自己摘 | ①② | 没提 | 让人扫一眼就抓住关键几行 |

结论：目标只覆盖了「降噪」和一部分「研判提效」；「先给结论」「依据就地」「判完落地」「经验沉淀」「结论可读」都是入口 2 补的。
