## 一、这类工作在干什么

配策略、接资产、升版本、管账号——共同点是：**用户在改系统的运行状态**。

扫之前先自问一句（问的是**当前这个场景 / 页面**，不是整个需求）：

> 这块界面上，用户在改什么？改错了是"不好用"，还是"会断业务"？

- 只是不好用 → 重心放在「看得懂、填得少」。
- 会断业务 → 「配不错、配完敢信」是必答，且比效率更值钱。

用这一句代替分类：判的是风险，不是给需求贴标签。

---

## 二、拔高方向（一句话）

> 别只让用户"把配置填完"，要让他"**改前心里有数、改时少出错、改完知道成没成**"。

效率只是其中一层，**结果可见** 才是这类工作更容易被漏掉、也更值钱的部分。

---

## 三、四条原则（判据）

扫需求时，逐条问右边的扫描问句。**发现"有问题"还不够，要定到具体是哪一种病**——病定了，点子才有方向。

| # | 原则 | 什么意思 | 常见症结 | 扫描问句 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | **看得懂** | 不懂术语也能配，概念、依赖、字段含义在配置现场就能搞清楚 | ① 字段名是内部术语，看不懂<br>② 不知道该填什么值，没有示例或默认<br>③ 不知道这项跟别的项什么关系 | 他配这一项，需不需要去别处查？ |
| 2 | **填得少** | 路径短、能复用、能批量，复杂留给系统 | ① 同样的内容反复填<br>② 相似对象要一个个配<br>③ 流程长，断了要重来 | 这件事他是不是第三遍做了？ |
| 3 | **配不错** | 错误在提交前被挡住，不靠配完试错 | ① 格式/约束错了，提交后才发现<br>② 跟已有配置冲突或被覆盖<br>③ 影响范围超出预期 | 他填错了，系统什么时候才发现？ |
| 4 | **配完敢信** | 配了什么、生效没有、对谁生效，一眼可查 | ① 不知道下发没有（过程不可见）<br>② 不知道对谁生效（范围不清）<br>③ 不知道效果对不对（结果不可验） | 提交之后，他怎么知道成了？ |

> 🛑 **别四条全上**：原则是扫描方向，不是验收项。一个需求里成立几条，取决于它改的是什么、错一次的代价有多大。

> ⚠️ **但"新建 / 配置 / 下发任务"类页面是例外**：这类页面用户往往只有一次机会成事（配错就下发错了），四条原则常常**全中**——演练案例 A（新建检测任务）就是四条全命中。这时不许按"主角原则"删掉三条，而是**按"错一次的代价"排优先级**：代价最高的 1~2 条做主角，其余降为基线补齐项，全都要做，只是不必都是亮点。
> 📌 判一句：**看错不致命（浏览、查数据）→ 挑主角；一次配错就出事（新建任务、下发策略）→ 全上。**

### 基线下限（这几条不用发散，缺了直接补）

| 对应原则 | 基线该有什么 |
| :--- | :--- |
| 看得懂 | 术语就地解释、填错有提示 |
| 配不错 | 字段级校验、依赖联动、危险操作二次确认 |
| 配完敢信 | 下发状态可见：下发中 / 已生效 / 失败原因 |
| 填得少 | 无（少填本来就是加分项） |

## 四、怎么往上想：换个做法

定了症结之后，**先别去看第六节的参考解法**。问一句：**这件事还能从哪儿变？**

下面六个地方都能变。变哪一处，做法就跟着换一种，不用凭空想。

> 🔗 **和 1.3 变维表的关系**：**这不是 1.3 通用六维的翻译，是本域自己的一张变维表。** 和通用六维（信息在哪层 / 走几步 / 上下文丢不丢 / 谁先动 / 什么时候给 / 默认状态）只是部分重叠——"谁来生成"对"谁先动"，"什么时候验"对"什么时候给"，"落在哪"对"信息在哪层 / 走几步"；**"输入方式""改的范围""要不要真生效"是本域独有的**。**直接用这张，不用回套通用六维**；这张发散不够，再拿通用六维补。

| 能变的地方 | 可以变成 | 变完大概到哪档 |
| :--- | :--- | :---: |
| 输入方式 | 表单 / 表格批量 / 导入文件 / 复制现成对象 / 自然语言 | 优化~创新 |
| 改的范围 | 单个 / 一批 / 分组 / 按标签 | 优化 |
| 谁来生成 | 人手填 / 套模板 / 系统推荐 / 系统生成人确认 | 优化~创新 |
| 什么时候验 | 填写时 / 提交前 / 下发后 / 持续 | 优化~创新 |
| 要不要真生效 | 直接生效 / 灰度 / 只记录不拦 / 影子并行 | 创新~变革 |
| 落在哪 | 页面 / 抽屉 / 弹窗 / 文件 / API | 基线~优化 |

两条用法：

1. **至少动两个地方，才算一条新做法。** 只改外观、只换容器（跳页改抽屉）不算。
2. **变完校验一句**：这条做法替用户省了哪份力——找、读、判断、重复、返工。说不出来，退回重想。

> 最后两行（要不要真生效、落在哪）是配置运维特有的，也是最容易出高水位点子的地方：只要允许"先不真生效"，很多"敢不敢配"的问题就化解了。

## 五、走一遍示例（示意走法，不是答案）

拿「配完敢信」的症结③"不知道效果对不对"走一遍：

| 变的地方 | 变出来的做法 | 档位 |
| :--- | :--- | :---: |
| 什么时候验 → 提交前 | 提交前预览：这条规则会命中哪些请求 | 创新 |
| 什么时候验 → 下发后 | 拿昨天的日志回放一遍，看会拦掉多少 | 创新 |
| 要不要真生效 → 只记录不拦 | 先进观察模式，只记录不拦截，看真实命中 | 创新~变革 |
| 要不要真生效 → 灰度 | 先在一小组资产上生效，看结果再全量 | 优化~创新 |
| 改的范围 → 一批 | 一次配多条时，先看整批合起来的效果 | 优化 |
| 谁来生成 → 系统推荐 | 系统给推荐规则，人只改差异部分 | 创新 |

> 🛑 这六条不是答案，是走法示范。换个需求，要重新拿症结从六处地方变，**不要回来抄**。

## 六、参考解法（只做参考，不是匹配源）

> ⚠️ **使用顺序**：先按第四节自己想一轮，再回来对照。这里的作用是**打开思路、查漏**，不是给答案。
> **不要拿它当匹配表**——从表里挑一条交差，等于放弃了思考。真用了，要能说出"这个需求为什么是它，而不是别的"。
> 表里的档位是估算，实际按体验目标的天花板重判；〔〕内为估算档位，（）内为适用 / 慎用条件。
> 🧮 **档位后面那句"还得出力"就是这档的依据**：创新档及以上的条目都跟了一句"用户还得自己出什么力"。**这句话写不出来，说明这条实际只到优化档，别往上报**；往 1.4 报水位时，直接用它答"人少干了哪件事、还剩哪件事"。

### 对应 1 · 看得懂

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :---: | :---: | :--- |
| 自然语言引导配置，把参数翻译成"你想拦什么" | 优化~创新｜还得出力：核对生成的规则对不对 | 判断 | 慎用：参数精细、顺序敏感的策略项，引导反而更慢 |
| 图解配置原理与依赖关系 | 优化 | 读 | 概念多、依赖绕才上图；两三个字段别画 |

### 对应 2 · 填得少

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :---: | :---: | :--- |
| 模板化 / 预置配置 / 推荐配置 / 一键套用 | 优化 | 重复 | 同类配置反复出现的场景 |
| 批量下发、批量修改、跨对象复制 | 优化 | 重复 | 策略、账号 |
| 导入导出、配置克隆、跨环境迁移 | 优化 | 重复 | 资产接入尤其 |
| 配置包 / 模板市场，团队之间共享配好的 | 创新｜还得出力：判断别人那套适不适合自己的环境 | 重复 | 多团队用同一套策略时才有价值 |
| 长流程化整为零：拆步骤、存进度、可中断续填 | 基线~优化 | 返工 | 长表单、跨概念才拆；三五项拆了更烦 |
| AI 生成配置草案 / 意图式配置：说目标，系统给规则 | 创新~变革｜还得出力：核对草案、备好回退 | 判断 + 重复 | 慎用：安全产品里人不敢用；必须配预览 + 回退 |

### 对应 3 · 配不错

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :---: | :---: | :--- |
| 策略重复 / 覆盖关系的可视化提示 | 优化 | 判断 | 策略类 |
| 影响面预判：改之前先列出会影响哪些资产、业务、用户 | 创新｜还得出力：判断这个影响面能不能接受 | 判断 | 策略、升版本 |
| 影响图谱反查：从一条策略反查会打到谁 | 创新｜还得出力：自己划掉不该打到的对象 | 判断 | 对象多、关系复杂时才成立 |
| 升级前兼容性预检 + 分批 / 灰度 | 优化~创新｜还得出力：决定先灰度哪一批 | 返工 | 升版本 |
| 配置仿真：拿历史流量或样本资产先跑一遍 | 创新~变革｜还得出力：判断跑出多少算可接受 | 返工 | 误拦代价大、又不允许试错时最值 |

### 对应 4 · 配完敢信

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :---: | :---: | :--- |
| **配置结果预览：最终生效形态先看再提交** | 创新｜还得出力：逐项核对，确认没写错 | 判断 | 全类通用，价值最高的一条 |
| 观察模式 / 影子并行：只记录不拦截，看真实命中 | 创新~变革｜还得出力：定期回来看命中，决定何时转正式 | 判断 | 想先观察、再决定拦不拦时最值 |
| 历史日志回放：拿昨天的日志看新规则会拦掉多少 | 创新｜还得出力：看回放结果判断误拦可不可忍 | 判断 | 想验证历史场景会不会被误拦时最值 |
| "谁在什么范围生效"的汇总视图 | 优化 | 判断 | 策略、账号 |
| 权限可核对：谁能做什么、为什么有这个权限 | 优化 | 判断 | 账号 |
| 配置漂移检测：实际跑的和配的不一致时自动发现 | 创新~变革｜还得出力：判断漂移是故障还是人改的 | 返工 | 配置会长期被人手工改来改去时最值 |

### 全类通用 · 具象化（把抽象变成看得见的）

> 这一组不按原则分，按"能不能画出来"分。用的时候先问：这件事在用户脑子里有没有画面？没有，就借一个物理过程。

| 参考做法 | 档位 | 省哪份力 | 适用 / 慎用 |
| :--- | :--- | :---: | :--- |
| 配置 = 一条可预览的路径：左边填，右边实时画出"终端 → 接入点 → 骨干 → 源站"，随填写变化 | 创新｜还得出力：照图核对填的值对不对 | 判断 | 链路类、路径类配置最适用 |
| 配置 = 一句能读回的话：把必填项串成"让上海销售访问 CRM 时走加速"，填完能读回来核对 | 创新｜还得出力：读一遍确认语义没跑偏 | 读 | 字段多、概念绕的场景才值得 |
| 配置 = 一张回执：配完给"改了什么、影响谁、有没有问题"的一张单子 | 创新｜还得出力：拿回执跟预期对一遍 | 判断 | 变更影响面大时最有用 |

> 🛑 **具象化不是画得花哨**：关键是画出来的形态，跟用户脑子里那件事的过程对得上；对不上，就只是装饰。

## 七、怎么用（三步）

> 📐 **扫描粒度：场景 / 页面 / 任务，不是"需求"**。
> 一个需求通常由多个场景和页面组成：有的页面在配策略，有的在看分析结果，有的在排障。**不要拿整个需求定性**，逐个场景判断里面的任务属于哪类工作；一个需求可以同时命中多类经验，四类互补、不互斥。同一个页面混着两类任务（如配置页顶部带生效状态概览），两类各扫一遍。
> 扫描结果按场景归档，回到 1.3 也按场景（Sx）落表。

> 🧩 **原则不是每个页面的验收单**：一个页面通常只承接其中两三条，剩下交给链路上的其他页面。

| 链路段 | 主要原则 |
| :--- | :--- |
| 入口（我要配什么） | 看得懂 |
| 填写（怎么配） | 看得懂 + 填得少 + 配不错 |
| 提交后（配成没成） | 配完敢信 |

> 反查用：哪条原则在所有页面上都没人承接，说明流程缺了一段。

1. **先问代价**：当前这个场景改的是什么，改错了会断业务吗？会 → 第 3、4 条原则必答，优先于效率。
2. **逐条扫，定症结**：用扫描问句一条条问，问出"用户还要出多少力"；对得上的，记到具体症结（①②③），别只写"这里体验不好"。
3. **变出做法，再对照**：拿症结对照第四节的六处地方，变出几条结构不同的做法；想完再看第六节，缺的补、重的删。还原成一句"让人……"，和入口 1（从体验目标抠）的结果**合并去重**，回到 1.3 第 3 步分档。

> ⚠️ 只走入口 1 的时候，第 4 条原则几乎不会被触发——目标里很少会写"配完要知道成没成"。这就是要单独扫一遍的原因。

## 八、扫描示例：GA 配置提效

> 示例只演示扫法，场景细节以实际需求为准。

| 原则 | 扫到的答案 | 症结 | 目标里有没有提 | 转成的突破点 |
| :--- | :--- | :---: | :---: | :--- |
| 看得懂 | 新增配置项术语多，得翻文档或问人 | ① | 没提 | 让人在配置现场就看懂这一项是干什么的 |
| 填得少 | 同类配置要一遍遍重复填 | ① | 提了（提效） | 让同类配置一次配完、能复用 |
| 配不错 | 约束不满足时，提交后才报错 | ① | 没提 | 让人提交前就知道哪里会出错 |
| **配完敢信** | 配完不知道下发没有、生没生效、对不对 | ①②③ | **没提** | **让人提交前先看到配完的样子**（本次演练漏掉的就是这条） |

结论：入口 1 只能扫出「填得少」；其余三条都靠入口 2 补出来，其中「配完敢信」是价值最高的一条。

## 九、待补

- **四类初稿已齐**：①配置运维 ②运营分析 ③排障闭环 ④价值感知。
- **待演练验证**：拿真实配置类需求跑，扫不出目标之外的东西，就改原则或改症结。只看跑没跑通，不看案例出处。
- **参考解法可长，但不追求穷举**：遇到新做法，补进对应原则下，标档位、省哪份力、适用 / 慎用；补的来源不限，但**不许当成默认答案**。
- **验收口径**：拿一个真实的配置类需求跑一遍，能稳定扫出「结果要可见、可预期」这类目标之外的机会点，才算这类经验可用。
