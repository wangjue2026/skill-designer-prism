# 4.1 业务解决方案架构、页面清单与框架选型指引 (Solution Architecture & Page Inventory)

> 💡 **中枢定位**：
> 本文档是【方案系统设计主线 · Part2】的主控与框架选型指引。
> 承接 1.4 选定草图方向与 1.3 突破点，将业务流程落地为**端到端最终解决方案蓝图**：
> 1. **明确解决方案包含哪几个页面/视图**（主页面、抽屉、弹窗的页面清单）；
> 2. **对齐页面模板库**（严格从 [`03-design-assets/page-templates/01-page-types.md`](../../03-design-assets/page-templates/01-page-types.md) 中选择标准页面类型 ID）；
> 3. **为每个页面产出界面布局线框图**（Wireframe Schematics）；
> 4. **将标杆设计经验（EP-xx）与真实 idux 组件进行分页面深度装配**，彻底避免信息孤岛。

## 零、方案落地前先定"度"：类型定性与严肃度（原 2.1 迁入）

> 📌 **为什么放在页面清单之前**：定性不改变"做什么"（那是 1.3 与 1.4 的事），但决定**克制到什么程度、能不能用红色、变更要不要二次确认**。这些一旦定错，后面所有页面的语气都会跟着错。

### 0.5 需求类型与严肃度

先判 `Type-0x`（对照 [`需求大类设计决策/00-总览与类型定性.md`](../②设计思考与决策/需求大类设计决策/00-总览与类型定性.md)），再按业务性质定"度"：

| 业务大类 | 严肃程度 | 典型场景 | 推荐审美风格与色彩基调 | 关键交互原则 |
| :--- | :--- | :--- | :--- | :--- |
| **可视化运维类** | 极高 (Mission-Critical) | 拓扑监控、故障自愈、流量调度、节点巡检 | **深沉克制 / 石墨冷灰**<br>底色通透、去框线化，色彩仅留给红/黄/绿告警脉冲 | In-situ 图内原地展开、视线锚定、三级联动排障流 |
| **策略与业务配置类** | 高 (High-Reliability) | WAF 规则集、BGP 路由划拨、安全拦截策略 | **严谨理性 / 逻辑清晰**<br>蓝灰主调、明确步骤条、高对比度参数表单 | 强配额预校验、严密防呆、变更前后对比 (Diff) |
| **对象与资源管理类** | 中 (Standard Enterprise) | 资产清单、主机列表、证书管理、用户鉴权 | **现代扁平 / 高效规整**<br>白底卡片、32px 高度紧凑搜索、40px 行高表格 | 冻结关键列、多维批量操作、高频快捷抽屉编辑 |
| **复杂报表与运营分析** | 中偏低 (Analytics) | 计费账单、流量大盘、访问趋势、SLA 达标报表 | **通透开阔 / 丰富可视化**<br>双色阶图表、KPI 四联胶囊、高亮离群值 | 多维时间切片对比、Top N 数据过滤、图表/表格一键切换 |

> 🛑 **严肃度只定"度"，不改"向"**：它不能因为"这事很重要"就把 1.4 定的结构推翻。它的作用范围只有三个——语气、克制程度、防呆强度。
> 📌 **一句判据**：**错一次会不会出事？** 会 → 走"极高 / 高"两档（防呆优先、色彩克制）；不会 → 走"中 / 中偏低"（效率优先、信息密度可以高）。

### 0.6 场景 ➔ 标杆 Job 对齐

从 1.1 的主场景 `S1~Sn` 出发，去需求大类分册看该类型沉淀了哪些标准 Job 节点，逐个对齐：

| 业务场景 | 场景名与核心痛点 | 匹配标杆 Job 节点 | Job 核心命题 | 该 Job 下值得关注的 EP |
| :--- | :--- | :--- | :--- | :--- |
| S1 | [名]（痛点 `🚩S1-Px`） | Job N | [这个 Job 要解决什么] | EP-xx、EP-xx |

> 📌 **对齐不到的怎么办**：写"未命中标杆 Job → 业务独立推导"，并在页面上显式标注 `<span class="deriv">业务独立推导</span>`，不许硬塞一个 Job 进去。
> 🔗 **与横向库的关系**：命中纵向分册走纵向（`EP-xx`）；未命中或分册未覆盖，按 [`横向库承接与场景拆解桥协议.md`](../../04-workflows-and-cases/横向库承接与场景拆解桥协议.md) 走横向（`D0x-EPxx`）。**这张表的"业务场景 + 痛点"就是桥协议 Layer A 的输入**（原 Layer A 里的"发力点 Ln"一栏，改用 1.3 的 `Bx`，见下文）。

## 三、Part2 标准交付契约（分页面装配，直供 5.0 汇流）

完成本步推导后，必须输出以下两大结构化内容，作为注入 5.0 设计说明书的硬性输入：

### 1. 最终解决方案架构与页面清单总览 (用于设计说明书 5.2 节)
* **页面清单表**：列明每个页面编号（`Page-01`, `Page-02`...）、页面名称、交互形态（主页/抽屉/弹窗）、模板类型 ID、承担的用户 Job、**承接的突破点（`Bx`）、来源草图（`方向X / Pn`）**。

> 🛑 **两张必查表（定稿页面清单前跑完）**：
> * **覆盖率自检**（业务对象 × 动作 / 状态全集逐项认领页面落点，落不了地的显式标"本期不做 + 原因"）—— 见 SOP Step 3；
> * **草图继承校验**（草图里的页面是否都在、页面数是否被私自扩张）—— 见下一条。

### 1.5 从草图继承：开工前先对一次账

> 📌 **为什么**：1.4 已经把方向定了、页面结构定了。4.1 若从零开始"重新想页面"，等于把用户刚选完的方向又改一遍，**这是主线里最伤信任的一种走偏**。

开工前，拿 1.4 的选定方向逐项对账：

| 对账项 | 判定 | 不通过怎么办 |
| :--- | :--- | :--- |
| 页面数量 | 草图画了几个页面，清单是不是就几个 | 少了 → 补齐或说明为何合并；多了 → **回 1.4 改方向**，不许在线框层擅自加页 |
| 主结构 | 草图是"一屏工作台"还是"列表+详情"，清单必须同构 | 不一致 → 停，回 1.4 重新确认，不许"做着做着觉得两页更好" |
| 进入关系 | 草图的"从哪进到哪"是否保留 | 变了 → 说明导航级改动，回 1.4 |
| 突破点落点 | 草图里圈的 `Bx` 在新清单里都有归属页面 | 有突破点无处落 → 要么补页面，要么明确"该突破点降级/本期不做 + 原因" |
| **档位是否被降级** | 草图定的档位（如 `B1 变革版`）在线框里要有对应机制，不许落成"优化版" | 改回；确需降档 → 回 1.4 重确认方向，并在清单里写明降到哪档 |
| **目标与指标是否同步** | 选高水位时声明的目标/指标变更，本步与 5.0 必须使用**改后的**版本 | 回 1.2 补录变更，不许沿用旧目标写新方案 |

> ✅ **一个健康的信号**：4.1 之后如果页面清单和草图的差异超过 30%，**不要硬推**，回 1.4 补一版草图——大概率是草图当时没想全，而不是草图错了。

### 1.6 物料装配：什么时候"装配"、什么时候"选型"

> 📌 **你的流程里"页面及物料装配"是独立一步**。它和"经验匹配"不是一回事：经验回答**用什么做法**，物料回答**用哪些现成件**。两者要分开判，否则会出现"经验选了抽屉，结果从组件库随便找了个抽屉"的脱节。

对每个页面，先定**装配清单**（要哪些物料），再定**具体选哪个**：

| 物料 | 先问"要不要" | 再问"用哪个" | 出处 |
| :--- | :--- | :--- | :--- |
| 页面模板 | 这页属于哪种骨架 | 从 `01-page-types.md` 选 ID；无专属则借用 + 注明参考案例 | [`page-templates/01-page-types.md`](../../03-design-assets/page-templates/01-page-types.md) |
| 组件 | 这处交互要什么能力 | 从 `idux-component-map.md` 映射真实组件名；查无则保留真实名 + 声明来源 | [`components/idux-component-map.md`](../../03-design-assets/components/idux-component-map.md) |
| 功能模块 | 是否属于高频通用能力（批量/导入导出/周期/标签/优先级） | 直接调 `feature/` 对应规范，不重新设计 | [`feature/`](../../03-design-assets/feature/) |
| 设计范式 | 这页有没有可套用的成熟范式（P-01~P-08） | 只在发力点已定后按本质反查，**不许反向用范式定发力点** | [`patterns/`](../../03-design-assets/patterns/) |
| Token | 需要定尺寸 / 色值 / 间距 | 优先沿用经验库案例 Token，其次资产库通用表 | [`tokens-cheatsheet.md`](../../03-design-assets/tokens-cheatsheet.md) |

> 🛑 **装配不等于凑齐**：一个页面用了 12 种组件不叫装配好，叫没想清楚。**物料数量应与该页承接的突破点数量成正比**（2 处突破点的页面，通常 5~8 个物料足够）。

### 2. 分页面全要素深度展开清单 (用于设计说明书第 7 节)
针对解决方案中的**每一个**页面/视图，依次结构化输出：
1. **页面定位与用户 Job**：该页面承担什么核心任务，翻转了哪几个现状痛点（插旗 `🚩Sx-Py`）；
2. **界面结构线框示意图 (Wireframe Schematic)**：清晰的布局线框，标注头部套头、筛选栏、卡片区、主表格/拓扑区、操作底栏等；
3. **承载的设计经验与 Why 因果**：明确本页面落地了哪几条标杆设计经验（如 `EP-01`, `EP-02`, `EP-04`, `EP-07`），说明为何在此采用此解法；
4. **页面模板与真实 idux 组件清单**：列明选用的模板 ID、所用真实组件（`IxTable`, `IxDrawer`, `IxProgress`, `IxPopconfirm` 等）、尺寸与 Token 硬指标（`h32`, `h28`, `rounded-[2px]`, `#1C6EFF` 等）；
5. **关键交互与状态流转机制**：原地闭环逻辑、实时计算或心跳防死信规则；
6. **与草图的一致性对账（在 4.1 内部完成，不进说明书）**：本页对应 `方向X / Pn` 的哪一个草图、哪些分区被完整继承、哪些做了偏离及其理由（偏离到主结构层面的，必须回 1.4 重确认，不能在此自行说明后放行）。

> 🔎 **为什么对账留在 4.1**：它是"方向没有被偷偷改掉"的唯一凭证；但说明书读者要看的是线框质量，所以对账结论留在本步，说明书只呈现页面清单与线框，页面头部不写一致性声明。

### 1.7 逐页经验匹配（原 2.1 第二遍，已并入本步）

> 📌 **为什么放在这里而不是单开一环**：经验要"逐页"判才准，而页面清单正是在这一步产出的。**在页面确定的地方判经验，是最省事也最不容易漏的位置**——单独跑一趟"回头再匹配"，往往会退化成把同一批经验糊到每一页上。

对每个页面，配经验之前先问四句：

| # | 问句 | 答不上来说明什么 |
| :---: | :--- | :--- |
| 1 | **这页用户要办成什么事？**（一句话，不是功能罗列） | 页面职责没划清，回 §1 重定 |
| 2 | **这页承接了 1.3 的哪几处突破点 `Bx`？** | 页面和突破点断链了——可能这页多余，也可能突破点漏了落点 |
| 3 | **这页对应哪个标杆 Job？该 Job 下有哪几条 `EP-xx` 正好治这个事？** | 对不上 Job → 标"业务独立推导"，不许硬塞 |
| 4 | **这条经验会不会改掉 1.4 定的结构？** | 会改结构 → 停，回 1.4 确认方向，不许在线框层偷偷换骨架 |

结果直接落在「分页面装配清单」里，不另开表：

| 页面 | 承接突破点 | 用户核心任务 | 对应 Job | 采纳经验 | 采纳理由（能说回 `Bx` 或 `🚩Sx-Py`） | 业务独立推导 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Page-01 | B1、B3 | [一句话] | Job 1 | EP-03、EP-04 | 新建要保留列表上下文 + 影响面要前置（对 B3） | 预置分组的命名与粒度 |

两条常见错判：

| 错判 | 长什么样 | 怎么改 |
| :--- | :--- | :--- |
| **一页堆满经验** | 一个页面采纳 8 条 EP，什么都要 | 按"这页最需要解决的那一件事"选 2~4 条，其余降为基线要求或不采纳 |
| **跨页复用被算两次** | 同一条 EP 在 3 个页面都写"采纳" | 允许，但要写清"每页落地的是它的哪一段"，否则等于没说 |

> 🔎 **判据**：每页至少一条"采纳理由"要能说回突破点 `Bx` 或痛点 `🚩Sx-Py`。说不回的，这条经验是顺手抄的，删掉。
> 📌 **与说明书的对应**：这张表直接按 5.0 第 6.2 节（单表穿透）+ 第 7 节各页的「设计经验与组件选型映射清单」表头落，不另建格式。
