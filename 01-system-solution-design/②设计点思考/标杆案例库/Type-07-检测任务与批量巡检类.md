## 一、需求类型认知

* **一句话定义**：以「任务」为主键，把分散的检测/扫描/巡检能力编排成一次**可周期调度、可复用、可追溯多轮历史**的作业，并通过任务清单持续暴露执行态与失败面。
* **它解决什么问题**：让“对一批对象施加一次检测动作”这件事**有载体、有归档、有追溯**。

### 【Job 1：创建并运行任务】
> **核心命题**：用户如何把"对一批对象施加一次检测"发起成可调度、可复用的作业，在配置期的多重约束下不被卡住，并在等待执行期间获得清晰的状态与结果反馈？
> 🔄 **覆盖流程**：`进入创建入口 ➔ 录入配置并圈选对象 ➔ 触发运行 ➔ 等待并观察执行态`

| 观察维度 | 核心考量 (Why it matters) | 前置思考性自检问句 (资深设计师通用思考母尺) | 可选解法空间 (行业通用解法矩阵) |
| :--- | :--- | :--- | :--- |
| **🔍 需求能力**<br>*(业务规则与完备性)* | 作业调度与配置的完备度、执行状态机与流转逻辑、能力/资源约束下的防冲突 | 1. **【支持能力与分支场景】**：本类需求需支持哪些作业发起方式（一次性触发 / 周期性调度 / 手动重跑）？一次作业的配置由哪几部分组成，各部分之间是否存在先后依赖？"作业内容"与"作用对象"分别有哪些确定方式（引用既有对象 / 手工圈选明细 / 按属性规则动态圈定）？是否支持由既有作业快捷派生？<br>2. **【执行状态与流转逻辑】**：一次作业从发起到收束会经历哪些状态？各状态间的流转条件与互斥关系是什么？处于非终态时，哪些变更类操作必须被禁止？<br>3. **【结果情况与配置依赖】**：作业结束可产生哪些定性结果（无异常 / 检出问题 / 部分对象未完成 / 整体失败）？结果能否按配置项回溯？<br>4. **【异常与边缘场景处理】**：执行者与"作业内容、作用对象"之间是否存在能力或连通性上的约束？这类约束应在什么时机暴露给用户？重复发起、资源占用与配额冲突如何防御？ | • `发起方式`：一次性触发 / 周期调度 / 手动重跑 / 有效期窗口<br>• `对象确定方式`：静态手工圈选 vs 按属性规则动态圈定<br>• `非终态处理`：严格锁定（只读） vs 允许终止后再操作<br>• `约束暴露时机`：配置期即时反馈 vs 提交后异步校验<br>• `资源保护`：并发限流 / 排队 / 超时处理 |
| **🧭 交互方式**<br>*(动线长短与易用防呆)* | 压缩长链路的心智负荷、消除操作悬空、让约束尽可能早地暴露 | 1. **【入口多深与步骤多少】**：发起一次作业需要几步？入口置于哪一层、是否显性？能否从相关上下文（对象清单 / 事件 / 详情页）直接发起？步骤是否还有压缩空间？<br>2. **【交互形式与状态展示】**：多字段配置用什么形态承载最合适（取决于字段数量与控件体量，而非固定形态）？海量对象用哪种选择控件最合适（取决于对象数量级与是否需要多维度筛选）？执行中的非终态如何在无需手动刷新时就地暴露？<br>3. **【操作反馈与高效设计点】**：提交后应停在哪、给出什么反馈，才能避免用户"不知道存没存上"并重复提交？若同一套配置既要能"存起来复用"、又要能"立刻跑一次"，出口如何组织才不会分散注意力？本环节还有哪些可提效 / 防错的设计点（更少的步骤、更早暴露约束、更轻的出口）？ | • `入口位置`：列表顶头一级显性 / 由上下文快捷发起<br>• `表单承载`：独立页面 / 弹窗 / 抽屉 / 单页表单（按配置项数量与控件体量选择）<br>• `对象选择控件`：穿梭选择 / 多选列表 / 下拉（按对象数量级选择）<br>• `出口组织`：单一主操作 / 主操作 + 次级选项分流<br>• `提交后去向`：返回列表并反馈 / 停留原页<br>• `状态暴露`：就地进度 / 需手动刷新 |
| **🎨 呈现布局架构**<br>*(物理承载与视觉Token)* | 形式追随数据特征、大对象量级的物理承载、扫视动线与样式一致性 | 1. **【旅程页面与UI展示形式】**：整个 Job 涉及哪几个物理页面（起点台账 → 创建页 → 回到台账看执行态）？台账容器依据字段特征（规整统一 vs 长短不一、是否成组）应选哪种？<br>2. **【首屏信息与信息量级】**：台账首屏应承载多少条？待选对象池量级多大（几十还是数十万）？创建页如何在常见分辨率首屏内避免横纵多重滚动条？<br>3. **【样式Token与视觉规范】**：台账容器与间距的尺寸规范是什么？异常条目用什么视觉抓手，既能被扫视捕获又不压盖内容？非终态与不可用态的样式规范是什么？按钮与表单控件的尺寸 / 圆角基线是什么？ | • `台账容器`：卡片 / 高密度表格（按字段是否规整、量级选择）<br>• `大对象量级承载`：分页 / 虚拟滚动 / 树表穿梭<br>• `异常抓手`：弱渐变底 / 中性底 + 语义色标签<br>• `非终态表达`：进度条 / 状态标签 / 置灰 + 说明<br>• `控件基线`：统一高度 / 圆角 / 内边距 |

### 【Job 2：查看结果与排查问题】
> **核心命题**：作业结束后用户如何快速掌握整体结果，顺着完整记录回溯多次执行，并就地排查到单个对象、把数据交付出去？
> 🔄 **覆盖流程**：`看整体结果 ➔ 翻明细证据 ➔ 钻到单个对象`

| 观察维度 | 核心考量 (Why it matters) | 前置思考性自检问句 (资深设计师通用思考母尺) | 可选解法空间 (行业通用解法矩阵) |
| :--- | :--- | :--- | :--- |
| **🔍 需求能力**<br>*(业务规则与完备性)* | 记录的可追溯性、多次执行的归集模型、结果定性与数据交付 | 1. **【支持能力与分支场景】**：需提供哪些结果查看与分析能力（整体统计、明细检索、按不同视角归类、结果导出、单个对象下钻）？<br>2. **【结果情况与定性】**：作业结束可产生哪些定性结果？是否需要把"有异常"与"无异常"明确区分开？无异常时界面如何做正向引导？<br>3. **【配置项与字段依赖（多次执行模型）】**：同一作业的多次执行，是各自成为独立记录，还是归集到同一作业下、形成可切换的历史轮次？切换轮次时明细与筛选条件如何联动？<br>4. **【异常与边缘场景处理】**：作业失败或部分对象未完成时，能否给出明确的失败归因？能否只针对未完成的对象单独重跑？结果为空时如何兜底？ | • `多次执行模型`：归集为同一作业的历史轮次 / 各自独立的记录<br>• `结果定性表达`：区分异常面与安全面 / 单一"完成"标签<br>• `导出范围`：继承当前筛选条件的所见即所得 / 全量离线生成<br>• `失败归因`：就地给出原因与定位入口 / 仅提示"失败" |
| **🧭 交互方式**<br>*(动线长短与易用防呆)* | 降低排查动线摩擦、轮次切换轻便、下钻就地闭环 | 1. **【入口多深与步骤多少】**：从台账进入结果明细需要几步？从明细下钻到单个对象的证据需要几步？从发现失败到发起重跑需要几步？<br>2. **【交互形式与状态展示】**：切换历史轮次用什么控件最合适（取决于轮次数量与切换频次）？下钻单个对象用什么形态（需避免丢失当前明细的筛选与阅读位置）？轮次 / 筛选切换后数据如何平滑刷新？<br>3. **【操作反馈与高效设计点】**：导出应导出什么范围，才能与用户当前所见一致？失败信息能否就地给出、不让用户再跳一次？本环节还有哪些可提效 / 防错的设计点？ | • `轮次切换控件`：轻量下拉 / 时间轴 / Tab<br>• `下钻形态`：就地抽屉 / 行内展开 / 独立页面<br>• `失败闭环`：就地给原因 / 提供直达入口<br>• `导出与所见一致`：继承当前筛选 / 全量 |
| **🎨 呈现布局架构**<br>*(物理承载与视觉Token)* | 结果区的空间分层、高密明细的承载、严重度的可扫视表达 | 1. **【旅程页面与UI展示形式】**：涉及哪些页面与容器（结果概览 + 明细承载 + 就地下钻）？概览与明细如何分层（上下切分 vs 左右分屏）？<br>2. **【首屏信息与信息量级】**：首屏需展示哪些核心指标？明细单屏应承载多少行？长滚动下如何保持表头与分页稳定？<br>3. **【样式Token与视觉规范】**：概览区与明细区的空间占比规范是什么？严重度 / 等级用什么视觉编码，才能在海量明细快速滚动时仍可纵向比对？下钻容器的尺寸与遮罩规范是什么？ | • `空间分层`：概览条 + 明细表（上下）/ 左右分屏<br>• `等级编码`：图形化计量 / 语义色标签 / 色点 + 文字<br>• `明细承载`：固定表头 + 分页 / 虚拟滚动 |

### 【Job 3：日常管理与模板维护】
> **核心命题**：存量作业与可复用资产不断累积，用户如何以最低摩擦做日常轻维护、对破坏性操作有足够防御，并把可复用配置从单次作业中解耦成可被多处引用的资产？
> 🔄 **覆盖流程**：`日常轻维护 ➔ 集中维护可复用资产`

| 观察维度 | 核心考量 (Why it matters) | 前置思考性自检问句 (资深设计师通用思考母尺) | 可选解法空间 (行业通用解法矩阵) |
| :--- | :--- | :--- | :--- |
| **🔍 需求能力**<br>*(业务规则与完备性)* | 存量的日常管护、可复用配置的解耦、破坏性操作的边界 | 1. **【支持能力与分支场景】**：需提供哪些存量管护操作（轻量改名 / 启停 / 手动重跑 / 受控删除 / 复制派生）？可复用配置是否需要从单次作业中解耦、成为可被多处引用的资产？<br>2. **【执行状态与配置依赖】**：资产被修改后，已引用它的作业是即时生效、提示升级，还是保持既有快照？作业处于非终态时，哪些管护动作必须被锁定？<br>3. **【结果情况与异常防御】**：执行删除后，关联的历史记录如何处置（连带删除 / 归档保留 / 保留统计）？删除有下游依赖的对象时，是否有依赖校验与影响面提示？<br>4. **【配置项与字段约束】**：可复用资产包含哪些字段？是否需要版本与变更记录？ | • `配置组织`：解耦为可复用资产（引用） vs 内嵌在单次作业中<br>• `资产更新策略`：版本快照解耦 / 动态继承<br>• `删除策略`：逻辑删除 + 数据受控保留 / 硬删除 |
| **🧭 交互方式**<br>*(动线长短与易用防呆)* | 高频轻操作的原地化、破坏性操作的分级确认与降噪 | 1. **【入口多深与步骤多少】**：高频轻操作（如改名）能否在主台账上一步完成、不必进入详情？资产库入口置于哪一层？<br>2. **【交互形式与状态展示】**：轻量改名用哪种形态（就地编辑 / 弹层表单 / 独立页面）？删除、重跑这类操作采用什么确认形态（轻量气泡 / 阻断弹窗 / 输入确认）？就地保存后如何给出不打断视线的反馈？<br>3. **【操作反馈与高效设计点】**：哪些操作可以就地闭合、避免跳页丢失上下文？重复性操作与破坏性操作能否复用同一套确认组件，只按风险调整文案与视觉强度？ | • `轻操作形态`：就地编辑 / 侧边抽屉 / 独立页面<br>• `确认分级`：轻量气泡确认（回显对象名）/ 阻断弹窗 + 影响面说明<br>• `反馈强度`：轻提示 / 强提示 |
| **🎨 呈现布局架构**<br>*(物理承载与视觉Token)* | 多容器分流、微交互组件的视觉秩序与规范 | 1. **【旅程页面与UI展示形式】**：涉及哪几个物理页面（主台账的就地管护态 → 独立的可复用资产库页）？主台账与资产库各自应选什么容器形态（取决于字段特征、是否需承载长详情、以及量级）？<br>2. **【首屏信息与信息量级】**：资产库单屏应承载多少条？体量多大？低频的维护入口在主界面的视觉权重如何保持克制？<br>3. **【样式Token与视觉规范】**：原地编辑输入框与微型按钮的尺寸规范是什么？浮层（确认框 / 菜单）的圆角、投影、字号与按钮尺寸基线是什么？资产明细表的表头 / 行高规范是什么？ | • `容器分流`：卡片 / 高密度表格 / 列表 + 详情（按字段特征与详情长度选择）<br>• `浮层规范`：统一圆角 / 投影 / 字号 / 按钮尺寸<br>• `维护入口权重`：次级入口 / 弱化处理 |

    - **【微组件复用】为什么删除、重测、模板操作复用同一套白底浮层**：同一模块内的高频轻操作若各造一套弹层，圆角/阴影/间距会漂移并抬高维护成本；统一复用「白底 / 圆角 `2px` / 阴影 `0 4px 16px rgba(30,35,43,.14)`」基线，仅按破坏性更换文案与图标即可。

#### 4.5 本案例的贡献与局限
* **贡献**：以「任务」为唯一主键，把原本没有载体的检测动作变为可调度、可归档、可追溯多轮的作业。最值得复用的三处骨架 —— ① 任务卡片流 + 失败整卡微渐变底 + 失败指标警示橙，形成"滚动扫视即定位异常"的视觉拉力；② 配置期**前置防呆收窄**（选定设备后待选资产 `143606 → 5` 并就地说明原因），把拦截从"提交时"前移到"选择时"；③ 模板库采用**「左卡片列表 + 右详情」主从结构**，兼顾高密扫视与长详情承载。
* **局限**：单产品来源；本轮未覆盖项见 **4.0 覆盖局限**。

#### 4.5 本案例的贡献与局限
* **贡献**：① 用**左右两栏**把"规则库"和"任务清单"同屏，规则卡直接暴露"检查项数 / 检查任务数 / 最近检查时间"，让"挑规则 ➔ 建任务 ➔ 看结果"一屏闭环；② 任务指标用**"通过率 % ＋ 分子/分母"成对表达**，只染红异常分子，兼顾比例与绝对量；③ 资产选择用**三档 Tab 切换异构对象类型**（分组/主机/容器集群），每档换最贴合的控件；④ 首次实测了**运行中态**——执行期把行内动作整组隐藏、只留详情与一格百分比；⑤ 检查项风险等级用**四档整块实色标签**（高危 `#F52727` / 中危 `#FA721B` / 低危 `#FDAA1D` / 通过 `#22B07B`）。
* **局限**：单产品来源；提交后去向、周期调度、通知、规则与任务联动、检查失败态与导出内容均未覆盖；见 **4.0 覆盖局限**。
