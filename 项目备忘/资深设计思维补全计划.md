### 4. 体验目标检视：避免低 level 目标

- **状态：已完成（2026-10-20）**
- **为什么**：**目标定得低，后面的突破点会跟着降智**（目标多大，天花板就多高）。原来缺少对体验目标的"检视 / 提级"动作。
- **本轮关键发现（用户提出）**：**目标为什么会定小？因为 1.1 的 Job 被拆碎了。**
  - 用户原话：*"主场景 job 不能太细，不能将局部任务型的概括为 job。job 要是一个任务的完整闭环，比如'完成初始化配置让业务可以跑起来'，而不是拆成'新建 xxx'。"*
  - 因果链：**`Job 拆碎 → 目标只能对着碎 Job 写 → 目标必然小 → 突破点只能在界面层打转 → 出不了创新版`**。
  - 所以这件事**不是 1.2 一个人的问题**，必须连 1.1 一起修——在 1.2 靠改字句救不回来。
- **四处改动**：

  | 文件 | 改了什么 |
  | :--- | :--- |
  | **1.1 第四节** | 新增「Job 的颗粒度」判据：Job 是**一段时间的完整工作**，不是一次操作。四条判据（有周期 / 有终态 / **不含操作词** / 能独立交给一个人）+ 五组"错误 vs 正确"对照（新建检测任务 → 日常定期巡检 …）+ **追一问自检法**（只做一半业务上会有什么后果？）+ 合并回 Job 的三句话问法。模板与示例的 Job 列全部改成"从 A 到 B 的状态变化"写法 |
  | **1.2 第一节** | 新增「前置：Job 颗粒度不对，目标不用往下写」——一票否决，含操作词即退回 1.1 |
  | **1.2 新增第二章「体验目标检视」** | 两道检视（Job 够不够宽 / 目标够不够高）+ **目标高度三档尺**（低·操作级 / 中·任务级 / 高·工作级，对应能撑到优化/创新/变革）+ **提级四问** + 三条打回规则 + 交付模板加「目标检视结论」必填块 |
  | **1.3 第八节** | 加「扫之前先看一眼 Job 的颗粒度」：动作决定命中哪类，**Job 的宽度决定能扫多高**；Job 太窄不在这里硬撑，退回 1.1/1.2 |

- **沉淀的两条判据**：
  > 1. **Job 名字里出现"新建 / 配置 / 查看 / 提交 / 导入"= 拆碎了。** Job 应该写成"从 A 到 B 的状态变化"。
  > 2. **判目标高低看"终态"，不看"用词"。** 提级靠"终点往后推"，不靠"形容词往上堆"——"配置更顺畅"改成"极致顺滑"档次没变，只是变虚了。
- **提级最有效的一问**：*"用户是被这一步难困住，还是被这一整件事不确定困住？"* ——操作层的问题是"烦"，工作层的问题是"**不敢、不确定、说不清**"，后者才撑得起创新/变革。
- **关联**：1.1 / 1.2 / 1.3。

### 13. 草图呈现：从"分析师报告"改成"设计师方案"（已完成 · 2026-10-20）

- **起因**：用户看过第一版样板后的原话——**"太复杂了，我没耐心看，全是字，好累。"**
- **诊断**：第一版把交付物写成了**分析师报告**（一句话结论 + 方向对比表 + 顶部台账 + 3 个方向），而不是**设计师方案**。信息密度高、前置铺垫多，图被压到很下面。
- **三条修正（已写进 1.4 §零 的铁律区）**：

  | 铁律 | 原来 | 现在 |
  | :--- | :--- | :--- |
  | **只给 2 个方案** | 2~3 个方向 + 对比表 | **首推 + 次选**，两个。选择过多不是好事 |
  | **不画基线版** | 四档全画 | **只画创新 / 优化版**，基线版只是地基，不需要被选择 |
  | **框里只放内容** | "查什么 · 系统已按研发机画像出草案" | 三个灰块标签。**解释性短语一律搬到方案依据** |

- **结构从"四段式"改成"两方案式"**：`方案一（标题 → 为什么这么设计 → 整套草图 → 方案依据 4 行）→ 方案二（同）→ 请选择`。**顶部所有前置信息、方向对比表全部删除。**
- **设计说明承担了原来的全部职能**：`基于「场景」，角色卡在「痛点」。所以我把「什么」变成了「什么」。代价是…`——3~4 句，120 字以内，必须点出来自目标还是来自这类工作的固有毛病。
- **术语同步**：全链路把"方向"统一改为"方案"（SKILL / SOP / 5.0 / 1.4 / README），避免文档里"方向"和"方案"混用。
- **沉淀的判据**：
  > **交付物是给谁看的，就按谁的阅读习惯写。** 给规划人员看方案，第一眼要是**方案和它的图**；把台账、对比表、前置结论堆在前面，等于逼他在看图之前先做一次阅读理解。

## 七、待议：闸门要不要改成"内部比选、不透明给用户"

> 🚦 **状态：讨论过，暂不改。当前 1.4 仍按"出两个方案给用户选"执行。**

### 起因

用户提出：**"是否必须停下来让用户确认？直接拿最好的方案去实现会怎样？"** 直觉是——常规需求没必要让人选，设计师按最优（创新版及以上）直接输出即可；但要保留方案共创时的思路碰撞。

澄清后用户的准确意思是：**"还是要做草图发散，只是不摊出来，直接基于最优方案走下面的流程。"**（即：判断照做，决策不透明化）

### 讨论中确定的部分

| 议题 | 讨论结论 |
| :--- | :--- |
| 闸门挡的是什么 | **不是"设计好不好"，而是"方向错了还能不能回头"**。所以判据不该是"事情大不大"，而是"不可逆程度" |
| 为什么不能全放开 | "最好的方案"往往是设计师自认为最好——同一需求不同人会给不同"最优"，因为优化目标不同（省人力 vs 改动小）。**涉及取舍时，"哪个更值"是业务判断，不是设计判断** |
| 共创不靠闸门 | 真正要共创时用户会主动说；把闸门当共创工具，会在不该拦的时候拦人 |
| 常规需求也要分层 | **纯补齐**（加列、加筛选、补弹窗）免发散；**小但有选择**（批量放哪、状态怎么表达）仍要发散，只是快 |

### 候选判据（三种，均未落地）

**A. 三行自检（最轻）**

```
我这次替用户做了一个主张吗？
   否 → 直接走
   是 → 这个主张错了，返工要多久？
          一小时能改 → 直接走，说明书留一句
          要重画     → 停下来问
```

**B. 按不可逆程度分三档**

| 情况 | 处理 |
| :--- | :--- |
| 结构无可岔空间（常规） | 不出双方案、不停，说明书注明"考虑过 X 未选，因为 Y" |
| 有可岔空间但代价都小 | 不出双方案、不停，直接选最省力的，留一句取舍 |
| 有可岔空间且**选了难回头**（换主结构 / 改导航 / 多角色受影响） | **必须停**，出双方案 |

**C. 按"用户有没有表达过偏好"判**

- 用户明确表达过偏好（"我们要尽量减少配置动作"）→ 顺着做，不用问；
- 用户从没提过，而方案里有一个**重大主张** → 这才是该停的时刻。

> 📌 三个候选共同的问题：**都在给"人"定规则，而规则越细越难执行**。B 的"主结构"边界模糊、C 依赖"重大主张"的主观判断。

### 留痕方案（两个维度，可并存）

| 留在哪 | 写给谁 | 写什么 |
| :--- | :--- | :--- |
| **说明书里一句** | 用户 / 评审 | "考虑过 X 方案，未选因为 Y" —— 回答"有没有考虑别的做法" |
| **单独内部留档** | 自己复盘 | 比选了哪几个、评分、放弃理由 —— 说明书里不该塞太多我们的推演 |

> 🛑 不建议"完全不停、也不留痕"：那样分不清"想过但没选"和"根本没想到"，而这恰恰是 1.3 要治的病。

### 触发条件（什么时候回来做这件事）

任一条出现时再动：
1. 跑真实需求时，**连续出现"停下来问，用户回一句'你定就行'"** —— 说明闸门成了噪音；
2. 反过来，**出现"没停直接做，做完方向不对、返工大"** —— 说明判据缺位；
3. 用户明确提出要"少问、直接给结果"。
